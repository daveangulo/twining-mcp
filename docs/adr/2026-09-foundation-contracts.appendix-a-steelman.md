# Appendix A — Steelman of the smallest evolution (Stage 0, workflow wf_f80a3b3b-ac2)

## The smallest evolution: **"Record Revisions"** — one 2.x release (target 2.17.0, config version 3)

Read against `docs/FOUNDATION-PLAN.md` (D1/D2/D5 + the 2026-09-05 annotations), `src/storage/sync/{record-export,record-ingest,sync-manager}.ts`, the lifecycle paths in `src/engine/decisions.ts`, and DD-12 in `docs/plans/2026-09-05-cross-host-sync-plan.md` §4.7. This is the steelman of option 1 in `2026-09-15-foundation-programme-plan.md` §3.3, answering the §3.4 stress test.

### Assumptions this design makes

- **A1** DD-13 holds: the server process never runs a git write. Read-only git (`rev-parse`, `rev-list`, `log`, `show`) is permitted — `sync-manager.ts:128-140` already shells out to `git rev-parse HEAD`.
- **A2** D1 holds: `twining.db` stays derived and gitignored; `.twining/records/**` stays the committed truth.
- **A3** No event log, no new transport, no daemon (W4 stays unbuilt), no new dependency.
- **A4** Additive JSON fields only. Old clients round-trip unknown keys (they `JSON.parse` → mutate → `JSON.stringify` the whole object), so a 2.16.x host does not strip new fields.
- **A5** Config version 3 + the shipped `FORMAT_VERSION_TOO_NEW` read-only gate (`file-store.ts:31-51`) is the old-client story, exactly as v2 did it.

### What ships

**R1.1 — Minimal host identity.** `~/.twining/host.json` = `{host_id: <ULID>, created_at}`. No crypto, no key ceremony. Sole purpose: make two concurrent revision chains distinguishable instead of a byte diff. ~40 LOC.

**R1.2 — Per-record revision stamp + in-record mutation ledger.** Every exported kind (decision, post, entity, relation, handoff) gains:

```jsonc
"rev":       { "n": 3, "id": "<ULID>", "parent": "<prev rev id|null>",
               "digest": "sha256:…", "host": "<host_id>", "at": "…", "op": "override" },
"mutations": [ { "rev": "<ULID>", "parent": "…", "op": "superseded", "at": "…",
                 "by_asserted": "human", "host": "…", "changed": { "status": ["active","superseded"] } } ]
```

`digest` is sha256 over the canonical bytes with `rev.digest` elided — reuse `stableStringify` (`record-export.ts:45-58`), so canonicalization is already shipped and deterministic. Stamping happens **in the stores' save paths** (`sqlite-stores.ts` `save()`/`updateStatus`, `decision-store.ts:120-208`), not in the exporter, so the db copy and the file copy are byte-identical.

**R1.3 — Revision-aware ingest replaces file-wins.** `record-ingest.ts:288-327` becomes a chain comparison:

| Relation of file chain to db chain | Action |
|---|---|
| file extends db (`db.rev.id` ∈ file ledger ancestry) | apply — today's behavior, now *justified* rather than asserted |
| db extends file | **keep db, re-export the file**, count `tree_behind` — this structurally kills the measured D14 file-wins lifecycle revert |
| diverged (common ancestor, both moved) | keep db as the serving value, write a **conflict sidecar** `records/conflicts/<record-id>/<file-rev-id>.json` holding the other side verbatim, set `contested: true`, post a scoped warning |
| digest ≠ ledger's last digest with no rev bump | treat as diverged (old client or hand edit) |
| file absent, no tombstone | **do not delete**; mark `tree_state='absent'`, count, warn |
| file absent, tombstone present | delete row; tombstone is permanent |

This **supersedes** the `LIFECYCLE_RANK`/`REVERT_WATCHED` heuristic (`record-ingest.ts:55-72`) with a structural rule — a net simplification, and it closes DD-8 (file-wins precedence) with something defensible.

**R1.4 — Tombstones.** `dismiss`, `removeEntities`, `removeRelations` stop unlinking silently; they write `records/tombstones/<target-id>.json` `{id, target, kind, op: dismiss|remove|purge, at, host, last_digest, last_bytes}` and then unlink the payload. Tombstones are separate filenames → they union-merge cleanly against any concurrent mutation of the payload, and "tombstone wins" is order-independent. `last_bytes` keeps the historical copy visible. `purge` is a separate explicit operation, documented as not reaching git history or uncontrolled clones.

**R1.5 — Producer idempotency keys.** Optional `client_event_id` on decide/post/record/handoff, persisted in the record with its `payload_digest` and a sqlite unique index. Same key + same digest → return the original id with `duplicate: true`. Same key + different bytes → `ID_CONFLICT` error, never a second record.

**R1.6 — Prerequisite validation and deferral at ingest.** Today `decide()` reports dangling `depends_on`/`supersedes` at *write* time (`decisions.ts:344-352`, `:414-428`) but ingest applies anything. New: on admission, resolve `supersedes`/`superseded_by`/`depends_on`/relation endpoints; unresolved → admit the row but flag `pending_prereq: [...]` and withhold it from authoritative serving, re-checked every ingest; `depends_on` cycles → `quarantined` with a reason. A valid scoped relation is admitted unchanged (positive control).

**R1.7 — Publication state from read-only git.** Batched `git ls-files`/`git diff --name-only HEAD`/`git rev-list --count @{u}..HEAD` classify each record `local-only | committed | pushed | unknown`. Surfaced per record and in `twining_status`. No git writes; DD-13 intact.

**R1.8 — Receipts as posts + sync disclosure.** Each ingest emits one deduped `ingest-receipt` post `{head_sha, inserted, updated, tree_behind, diverged, absent, quarantined, host_id}`, and `twining_status` gains a `sync` block. Warnings for diverged/absent/quarantined reuse the 2.15.0 scoped, deduped, txn-wrapped warning machinery already in `record-ingest.ts:338-426`.

**R1.9 — Migration.** Forward migrate stamps `rev.n=1`, empty ledger, and `evidence: "legacy_unverified"`; `why`/`assemble` render the marker. `src/migrate/reverse.ts` already exists (sqlite → file layout, with a pre-reverse backup and a freeze warning) — it gains ledger-aware folding plus interrupt/rollback/forward-recovery tests.

**R1.10 — Merge policy + conflict harvesting.** `.gitattributes` ships `records/decisions/**/*.json -merge` (and handoffs/graph) by default — *mutable* kinds only; posts stay mergeable because they are create-plus-resolve. Ingest's 2.16.1 retain-on-unparseable guard (`record-ingest.ts:254-282`) is extended: when a file carries conflict markers, parse **both** hunks into conflict sidecars rather than only skipping.

**Cost:** ~1,200–1,800 LOC plus tests, no new dependencies, one config-version bump, no MCP schema breaks beyond additive fields. Roughly 3× a 2.16.1. Genuinely one release.

### What it buys (do not discount this)

It removes two *field-confirmed* data-loss classes — the file-wins lifecycle revert (D14) and row deletion on checkout — makes deletion propagate deterministically and survive replica reconnect, makes retries safe, makes dangling and cyclic prerequisites explicit instead of dropped, and pays down DD-8 and half of DD-12, all without touching the transport, the daemon question, or the dependency floor.

### The single structural defect

**The record file is simultaneously the current state, the history of that state, and the merge unit.** When two hosts mutate one record, `git merge` — a text-level, human-resolved, last-writer rule — is the authority, and it runs *before* any Twining code sees the bytes. The revision chain can only *detect* the collapse afterwards, and only on a host that independently retained the losing side in `twining.db` — the cache this architecture defines as derived, gitignored and rebuildable. So the evidence that a loss occurred is non-durable and non-replicable: `rm twining.db` and restart, an operation the design advertises and CI exercises, erases it.

Note the second-order cost: the ledger *increases* conflict frequency, because every concurrent mutation now touches the same array tail. Today's "disjoint non-adjacent edits merge textually but are semantically unverified" (the 2026-09-05 measurement in the D2 annotation) becomes "every concurrent mutation is a human conflict" — safer, and exactly the friction profile that got `-merge` rejected as R-3.

### Correction to the programme plan's §3.4 expectation

The plan predicts the failing set is "C14/C16/C20 + the measured file-wins revert." Two of those are wrong:

- **C20 passes** under this design (tombstones are the right shape for it, and they are cheap).
- **C21 passes** (the existing verify-gated, non-destructive migrate plus the existing `reverse.ts` already carry most of it).
- **The file-wins revert is closed**, not merely mitigated.

The load-bearing failures are **C11 and C14**, with C10, C16 and C22 failing by inheritance from them. §3.4 should be corrected to that set before it is used as the justification for the foundational change — the argument is narrower than written, and stronger for being narrow.


## Case verdicts

| Case | Verdict | Why |
|---|---|---|
| C10 | fails | Two of four clauses hold, two cannot. HOLDS: identical retries are deduped by client_event_id + payload_digest (R1.5), and a correction delivered before its predecessor is held as pending_prereq rather than applied blind (R1.6) — today ingest applies it and leaves a dangling superseded_by. FAILS on 'reconciled receipts' and on the acknowledgement boundary, because there is no channel from consumer back to producer. Sequence: host A posts P1 (client_event_id=k), exports, commits, pushes. Host B pulls, ingests P1, emits its ingest-receipt post — into B's working tree, uncommitted, because the server never commits (DD-13) and the operator drains .twining/ rarely or never (the documented normal case, docs J-7). A's twining_status can now report P1 'pushed' but delivery 'unknown' forever: it is structurally unknowable. A, believing the correction was lost, re-issues override(X) with a fresh key; that is a legitimate new operation, so dedup does not fire; X now carries rev n=3 on A while B holds n=2. When the branches merge, the two chains diverge and a human picks one — see C11. The receipt mechanism also regresses infinitely: the receipt is itself a record with the same delivery uncertainty and no receipt of its own. |
| C11 | fails | Both histories do not survive in the durable export, and replicas do not converge independent of arrival order. Sequence: A and B disconnected. A: override(X) -> X rev r2a (parent r1), status overridden, ledger entry appended. B: decide(Y, supersedes: X) -> Y.json is a new file (unions cleanly, fine) plus X rev r2b, status superseded, superseded_by Y, ledger entry appended at the same array tail. Both branches push; someone merges. Both sides changed `status`, the whole `rev` object and the `mutations` tail — adjacent-line edits, which the project's own 2026-09-05 measurement records as conflicting; the ledger guarantees the adjacency. A human resolves, and the reflex on a state file is `--ours`. The merge commit's tree now holds X@r2a only; r2b exists nowhere in the tree. Now ask three replicas what X is: a FRESH CLONE at the merge commit with an empty db ingests X as 'overridden', uncontested — no divergence is detectable because there is no prior chain to compare against, and the durable export is the only input (this is exactly the go/no-go's 'reconstruction from durable export'). Host A: 'overridden', uncontested. Host B: db r2b vs file r2a -> diverged -> contested + sidecar, but only while B's twining.db survives; `rm twining.db` and rebuild, and B agrees with everyone else. Three replicas, three views, and the only 'correct' one is held in a store the architecture calls disposable. Conflict harvesting (R1.10) does not save it: after a squash merge or a rebase there is no second parent to harvest from. |
| C14 | fails | The silent half is genuinely fixed and the resurrection half is not. FIXED: a branch switch no longer deletes rows (absence marks tree_state='absent' instead of DELETE at record-ingest.ts:329-334); a `reset --hard` past a mutation is now detected as 'db extends file' and the db wins with the file re-exported, which kills the measured D14 revert; cherry-picking a mutation whose ancestry is missing is detectable because the record carries its own rev.parent chain — genuine wins. FAILS on durability of that detection. Sequence: A decides X, ack returned, commits it. Operator later `git reset --hard HEAD~1` (or a teammate force-pushes and everyone resets). X.json leaves the tree; A's db keeps the row and warns — visible, good. Then A's db is rebuilt: `rm twining.db` and restart, the documented recovery path, the same path every fresh clone takes, and the path the plan's own DP3 makes mandatory ('drop db, rebuild from events, identical projection'). The rebuild reads the tree, X is not there, and nothing anywhere records that it ever was. A loss that was reported five minutes earlier is now unreported and unrecoverable. Second sequence, resurrection: cherry-pick a pre-tombstone commit onto a branch that lacks the tombstone file; the payload returns and, on any replica whose tombstone set has not arrived, the record serves as current again. |
| C16 | fails | The mechanical half is achievable in one release; the case still breaks. ACHIEVABLE: archive-is-not-revoke already holds via `archived_from` (types.ts:114-120) and unarchive restores the prior status, so a provisional never returns ratified; adding `revoked`/`retracted` statuses and a per-part status map over `constraints[]` (the only list with rule-like semantics) is an additive schema change, though every read path that renders constraints must honour it or a revoked constraint silently re-enters agent context. BREAKS on the interaction with the merge unit. Sequence: X is a five-constraint decision. Host A archives X (status=archived, archived_from=active). Host B, disconnected, revokes constraint 3 via partial supersession, then revokes X entirely. Both hosts touched `status`, `rev` and the `mutations` tail -> conflict on merge -> human takes A's archived version -> B's revocation exists in no tree. Later `twining_unarchive(X)` faithfully restores archived_from=active, and X serves as active with all five constraints including the revoked one. 'Restore cannot resurrect revoked authority' is violated by the merge, not by the restore code. Separately, 'only AUTHORIZED parts change' is unverifiable in this change set at all: overridden_by and promoted_by are caller-supplied strings (decisions.ts:1082-1090, :1207) — source-evidence gap 6 — so any agent can author any part-revocation. |
| C20 | satisfies | This is the case the small evolution does best on, and the programme plan is wrong to list it as a predicted failure. Tombstones (R1.4) have the right shape: a tombstone is a SEPARATE filename, so it union-merges cleanly against any concurrent mutation of the payload; 'a tombstoned id is never re-inserted' is order-independent, so arrival order cannot resurrect; the tombstone set is permanent, so a reconnecting old replica that still carries the payload file is reconciled on its next ingest; `last_bytes` + `last_digest` inside the tombstone keep the retained historical copy visible, which the case explicitly asks for; a backup restore predating the tombstone brings the payload back but the tombstone is in the tree and wins. Purge is a distinct explicit operation, documented as not reaching git history or uncontrolled clones — which is precisely 'do not falsely claim erasure'. Two conditions make this a verdict rather than a hope: (1) the R1.3 'db extends file -> re-export' rule MUST be suppressed for tombstoned ids or the reconciliation resurrects them — one guard, easy to get wrong, needs a dedicated test; (2) a replica sitting on a branch that predates the tombstone still serves the record while on that branch, which is a branch view and must be labelled as one rather than called current. |
| C21 | satisfies | Most of this already exists and the delta is small. Existing: migrate is verify-gated and refuses to finalize on a read-model mismatch, backs up the whole legacy tree to .twining/legacy-v1/, never deletes, and is re-runnable, so an interrupted migration is already a no-op on retry; `src/migrate/reverse.ts` already implements sqlite -> file-layout rollback with a pre-reverse backup and an explicit freeze warning; `FORMAT_VERSION_TOO_NEW` (file-store.ts:31-51) already makes an old client read-only, so with config version 3 old clients cannot corrupt unknown semantics. Delta: stamp rev.n=1 + empty ledger + evidence:'legacy_unverified' at forward migrate; teach reverse.ts to fold ledgers; add interrupt/rollback/forward-recovery tests. Post-upgrade records survive a rollback because 2.16.x preserves unknown keys across its parse-mutate-stringify round trip, and an unstamped mutation by a rolled-back client is later detectable as digest-not-equal-to-ledger's-last-digest — you learn THAT it changed and have field-level history up to rev n, which is enough to present the record honestly. Two caveats that do not break the case's literal invariants but should be stated: 'mark legacy authority ambiguity' is only meaningful once evidence classes exist, since every post-upgrade write is equally caller-asserted — the marker distinguishes legacy from new, not verified from asserted; and an unrendered marker is not a mark, so the `why`/`assemble` rendering must ship in the same release. |
| C22 | fails | Two of the four named triggers are cheaply handled; two are not. HANDLED: cyclic depends_on -> quarantine with a reason; dangling supersession -> already reported at write time (decisions.ts:414-428, the D10 work) and now deferred rather than applied at ingest (R1.6), re-checked each pass; a valid scoped relation is admitted unchanged, so the positive control passes; nothing is silently dropped, which is a real improvement over today's blind ingest. FAILS: (1) 'unauthorized cross-scope relation' is undetectable, because relation records carry a caller-supplied agent_id and no binding to an authorized scope — there is no principal whose authority could be exceeded, so an unauthorized relation is byte-identical to an authorized one, and rejecting on scope shape alone would reject legitimate cross-scope links (the positive control the same case demands). (2) 'competing corrections' inherits C11 verbatim: two hosts correcting the same record collapse to one at git-merge time, so 'no invented resolution' is violated by the merge driver before Twining runs. Sequence: A and B both correct decision X's scope from src/auth/ to src/; both edits land on the same `scope` line and the same ledger tail; the human resolver picks one; the tree records a single uncontested correction and no record of a competition having occurred. |
| R05 | fails | Representation improves substantially: the ledger preserves prior status values with who/when/what-changed, contested state becomes representable via the sidecar plus a `contested` flag, revocation and retraction become first-class statuses, archival-is-not-revocation already holds, and — importantly — authority stops depending on wall-clock, because revisions are parent-linked rather than timestamp-ordered. Two clauses still fail, both for the C11 reason. 'Preserve prior evidence' / lossless: the ledger lives INSIDE the file whose overwrite it was built to survive, so losing the merge loses the history along with the state it documented. 'Concurrent equally authoritative contradictions remain visible unless a defined authorized rule resolves them': the resolving rule is `git merge` plus a human with a text editor, which is neither defined nor authorized in any sense R05 means, and 'arrival order ... cannot settle authority' is violated exactly because whoever merges second is the one who chooses. A revision stamp converts an undetected loss into a detected one on one host; it does not make the loss not happen. |
| R07 | unclear | Genuinely close on the local half, and I want to be explicit about which way I would rule. SATISFIABLE: stable producer identity plus payload digest, retries with no duplicate semantic effect, and 'reused identity with conflicting bytes is an explicit conflict' all fall out of R1.5; backpressure, failed writes and gap visibility fall out of R1.8's counters and status block; consumer-side replay is already idempotent by ULID. DEFENSIBLE CONTRACT: the durable acknowledgement boundary can be declared as 'the sqlite write transaction committed', with the export tree a best-effort mirror repaired by a startup db->tree reconciliation — worth noting the FOUNDATION-PLAN already claims this self-healing exists ('a lost write is self-healing on the next twining_housekeeping') and it does not: there is no backfill path in src/, only forward.ts uses RecordExporter outside the write wrappers, so a crash between `inner.append()` and `exporter.post()` in withRecordExport leaves a db row with no file and today the next ingest DELETES the row. Fixing that is real and cheap. WHAT KEEPS IT FROM 'satisfies': there is no atomic boundary across sqlite and the filesystem, so the ack covers only the writer's own db, while the export tree is the SHARED truth — an acknowledged write is durable to its author and merely probable to every other reader. Whether that counts as satisfying R07 or as relabelling the failure is the validation owner's call; my own reading is that it satisfies R07 single-host and fails the 'no silently lost acknowledged event' clause the moment a merge or a db rebuild enters, which the requirements list as a rejection condition. |
| R08 | fails | R08 asks for eight states modelled independently. This change set can observe four and cannot observe the rest. OBSERVABLE: local persistence (the db row plus tree_state); queued transfer (R1.7's read-only git classification local-only/committed/pushed is genuinely new, cheap and honest); materialization (the consumer's own ingest counters); admission validation locally (R1.6). NOT OBSERVABLE, by construction: remote receipt, validated admission AT the remote, and task-level acknowledgement, because the only path from consumer back to producer is a receipt file that a human must commit and push and the producer must pull — unbounded latency, no completion guarantee, and no receipt for the receipt. Cursors: the consumer cursor today is a single in-memory `lastHeadSha` (sync-manager.ts:38) that is lost on restart; persisting it plus a per-record last-applied rev is cheap and should ship. The producer cursor R08 actually wants — 'what has any consumer admitted' — is undefined and stays undefined. Partition, reconnect and offline behaviour have no queue model at all: the queue IS the operator's git index, which Twining neither owns nor observes. Permission changes are not modelled anywhere. Clock skew genuinely improves (parent-linked revisions). Net: the seven-plus-state machine collapses to three real states — local, published, unknown — and 'state consistency and availability guarantees precisely' cannot be written down for the unknown one. |

## Strongest case for

It closes both field-CONFIRMED data-loss classes for roughly one release of work, and it does so structurally rather than heuristically. The revision chain replaces the `LIFECYCLE_RANK`/`REVERT_WATCHED` guesswork in record-ingest.ts with a real ancestry test, so the measured D14 file-wins revert stops being a warning and becomes an impossibility; absence stops deleting rows, so a branch switch no longer silently drops admitted state; tombstones make deletion propagate deterministically and survive replica reconnect (C20 — which the programme plan wrongly predicts as a failure); idempotency keys make retries safe; prerequisite deferral stops ingest applying corrections whose predecessors have not arrived. It touches no transport, needs no daemon, adds no dependency, breaks no MCP schema, preserves every already-ruled invariant (server never commits, db derived, creates union-merge), and retires two named open design decisions (DD-8, half of DD-12) with answers that are defensible rather than deferred. Against a five-lane programme whose own top risk is scope explosion, this captures most of the measured harm reduction at a small fraction of the cost, and it leaves the foundational change available later on a strictly better-instrumented base: after one drain cycle, R1.8's counters give the #12 conflict census that DD-12 says it is waiting for. If the field's actual pain is the three incidents that have actually happened, this is the option that fixes them this month.

## Strongest case against

It violates R05, R07 and R08 by construction, not by omission, and the violation is one sentence long: the record file is at once the current state, its own history, and the merge unit — so `git merge`, a text-level rule resolved by a human under time pressure, is the authority, and it executes before any Twining code sees the bytes. Everything the design adds can only detect the collapse afterwards, and only on a host that independently retained the losing side in `twining.db` — the store this architecture defines as derived, gitignored and rebuildable. That makes the proof of a loss non-durable and non-replicable: `rm twining.db` and restart, the documented recovery path and the plan's own mandatory rebuild test, erases it; a fresh clone never had it. So the guarantee cannot be stated in the form R08 demands, and the go/no-go's 'reconstruction from durable export' yields a confidently wrong, uncontested answer on exactly the records where two people disagreed. Worse, the mechanism is self-defeating in use: appending to an in-record ledger puts every concurrent mutation on the same array tail, converting today's quietly-mis-merged disjoint edits into a human conflict on every concurrent lifecycle write — the friction profile that got `-merge` rejected as R-3 — so the option's cost lands on operators while its guarantee still does not hold. The only fix is to stop letting two writers share a filename, which means mutations become their own files, which is the event log. Shipping this first is defensible as harm reduction; presenting it as satisfying the foundation requirements would be an overclaim, and R05/R07's non-negotiables are listed as rejection conditions, not as scores.
