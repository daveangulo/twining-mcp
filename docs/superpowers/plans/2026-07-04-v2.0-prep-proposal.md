# v2.0 Prep — Proposal (NOT approved for shipping)

Status: **proposal only.** Per the standing gate, nothing here ships without explicit go-ahead. Companion to docs/FOUNDATION-PLAN.md (D1–D7, W-series); this covers the v2.0.0 cut specifically: default backend flip, engines >=22.13, config version 2, and the rollout sequencing.

## Where we are

Everything v2.0 depends on has shipped and soaked-or-is-soaking in 1.x:
- W0.4 version gate (read-only on `config.version > 1`) — in the field since 1.21.0 (2026-07-02).
- SQLite backend, opt-in, warn-and-fallback — 1.21.0, hardened by the multiwriter soak.
- Git sync both halves: export tree + startup ingest (1.21.0), live re-ingest + content-hash re-embedding (1.22.0).
- `twining-mcp migrate` files ⇄ sqlite, verify-gated, idempotent — 1.23.0, acceptance-proven on this repo's own corpus.

What v2.0 actually adds is small in code and large in defaults: **the flip**.

## The one hard technical problem: the default flip must not strand legacy data

`DEFAULT_CONFIG.storage.backend = "sqlite"` alone is wrong. An existing file-backend project with no explicit `storage:` key would resolve to sqlite on upgrade and boot against an **empty database** while its real state sits in `blackboard.jsonl` — silent amnesia, the worst possible v2 first impression.

Proposed resolution rule (v2 server, when config has no explicit `storage.backend`):

1. `records/` tree or `twining.db` present → sqlite (already-migrated or sqlite-era project).
2. Legacy files with content present (blackboard.jsonl non-empty, or decisions/index.json non-trivial) and no sqlite state → **files**, plus a one-line startup nudge: "run `twining-mcp migrate` to move to the v2 backend."
3. Fresh project (nothing yet) → sqlite; `initTwiningDir` stamps `storage.backend: sqlite` explicitly into the new config.yml so the choice is visible and committed.

So the flip lands fully for new projects, and existing projects flip only through the verify-gated migrate — never implicitly.

## Rollout sequence

1. **Dogfood first, before any v2 code**: migrate THIS repo's `.twining/` for real (opt-in backend, 1.23.0 tool — no v2 needed) and commit the records/ tree. We become user zero of our own migration on live state, with the reverse path as the escape hatch. This also converts the golden-fixture test's corpus into a continuously-exercised production instance.
2. Build V1–V5 on a branch; full gates (suite, SOAK_SCALE=5, evals — see below).
3. **`v2.0.0-beta.1` published under dist-tag `next`** — never `latest`. Unpinned `npx -y twining-mcp` users (the README's install path) stay on 1.23.x; beta users opt in with `twining-mcp@next`. Plugin untouched.
4. Beta dogfood on ≥2 real projects (plan-doc requirement) + this repo. Watch for: fallback-divergence reports (old Node → files while teammates are on sqlite), migration verify failures in the wild, startup-latency complaints.
5. **Evals before beta→stable**: run the LLM-judged coordination evals (key-gated, test/eval/) against v2 vs the 1.23 baseline — the plan's testing strategy names this as the cheap-insurance comparison.
6. `v2.0.0` stable to `latest`. Release notes lead with the Node floor and the migrate command.
7. Plugin 1.11.0 pin bump — one release later, after stable has a quiet week. Plugin users are the most passive population; they go last.

## Decision points — yours to make

1. **Auto-migration at startup?** FOUNDATION-PLAN says the v2 server auto-runs migration on legacy layouts. I recommend **against full-auto for v2.0**: it surprise-mutates a *tracked* config.yml and drops a records/ tree into the working diff of everyone's repo the first time one teammate upgrades. The plan doc predates the standalone CLI; now that `migrate` exists with printed instructions, a startup **nudge** (option a) is the conservative default, with `TWINING_AUTO_MIGRATE=1` or `storage.auto_migrate: true` as an explicit opt-in (option b). Full-auto (option c) stays available for v2.1 if beta feedback demands it.
2. **Dogfood-migrate this repo now** (pre-v2, needs nothing new)? Recommend yes — it's reversible and it's the strongest possible soak signal.
3. **Node floor semantics**: hard `engines` bump with npm's soft warning + the existing warn-and-fallback keeping old-Node sessions bootable on the file backend (recommended — a coordination server must not brick a session), vs `engine-strict` refusal.
4. **Beta channel**: dist-tag `next` (recommended) vs straight to `latest`. Only `next` protects the unpinned-npx install base.
5. **Go-stable timing**: the gates above, or a fixed date you prefer.
6. **Version-2 stamp timing**: at v2-migrate finalize (recommended — it's the mixed-team lockout W0.4 exists for) vs deferring the stamp to v2.1.

## Strongest alternative considered

Ship v2.0 as "engines bump + version-2 machinery" and defer the default flip to v2.1. Rejected-as-recommendation: with the legacy-detection rule, the flip only affects *new* projects immediately, so the stranded-data risk the split would mitigate is already contained — and the flip is the payoff the entire W-series was sequenced for (design review: storage findings A1–A6 fixed *by default*, not just for opt-in users). But it's the honest fallback if beta surfaces resolution-rule bugs.

## Risks

| Risk | Mitigation |
|---|---|
| Default resolution rule mis-detects an edge layout (empty legacy files + no sqlite state, hand-rolled dirs) | Three-branch parameterized tests + beta; misdetection lands on `files` (safe) in the ambiguous branch |
| Old-Node teammate silently on files while team is on sqlite (fallback divergence) | Loud startup warning already exists; upgrade guide names it; stragglers are re-migrate-able by design |
| `latest`-flip surprises unpinned npx users | Beta on `next`; stable release notes lead with the floor; server still boots on old Node via fallback |
| Auto-migration surprise (if option c ever chosen) | Recommendation is nudge-first; any auto mode is explicit opt-in in v2.0 |
| Publish workflow doesn't support prerelease tags today | V1 includes the `next` dist-tag change; test with a `v2.0.0-beta.1` tag on a throwaway package first? No — dry-run mode of publish.yml exists (workflow_dispatch input) |
