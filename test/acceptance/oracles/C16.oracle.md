# C16 Oracle — Partial supersession, revocation, archival, restoration

**Status:** oracle v1.0.0, authored 2026-09-15 by the independent validation owner, *before* any test execution.
**Sources used:** `acceptance-cases.md` (C16 row, coverage map, go/no-go), `requirements.md` (R05, R06, R19 primary; R02, R03, R07, R08, R12 touched), `01-foundation.md` §"Required proof before broad implementation".
**Non-derivation statement:** No implementation source, schema, plan or design doc was read. Any term below that happens to match an implementation identifier is coincidental; the system under test (SUT) must supply a declared total mapping from its own vocabulary onto the abstract observables in §3 *before* the run.

---

## 1. What C16 must prove

C16 row: *"Partial supersession of a multi-part decision, revocation, archival, then restoration → Only authorized parts change. Archive is not revoke; restore preserves prior lifecycle and cannot resurrect revoked authority or promote provisional data."*

Decomposed into four independently falsifiable claims:

| Claim | Requirement anchor |
| --- | --- |
| K1 — A supersession touches exactly the parts inside its authorizing scope; neighbouring parts keep state, anchor and version identity. | R06, R05 |
| K2 — Archival changes surfacing/retention only; it changes no part's authority state, and it is distinguishable from revocation in both the current and historical views. | R05, R19 |
| K3 — Restoration (unarchive of a record **and** rebuild of a store from a durable export) replays prior lifecycle faithfully: revoked stays revoked, provisional stays provisional, anchors stay at their original revisions. | R05, R19, foundation proof bullets 1/4/5 |
| K4 — A lower-authority actor cannot obtain, by supersession claim or by riding along in an archive/restore, an authority it did not have; and delivery/admission receipts never become acceptance. | R03, R04, R05, R08, foundation proof bullets 2/3 |

## 2. Assumptions (declared for challenge before the run)

- **A1.** Authority is scope-delegated and declared by the oracle (§4 matrix), not discovered from the SUT. If the SUT has no delegated-authority model, the run is executed with `usr_juno == usr_hera` and that substitution is reported as a coverage gap for K1's authorization half (the scope half still runs).
- **A2.** The SUT exposes, by whatever means, the four observables of §3. A SUT that cannot distinguish *historical* from *current applicable* answers fails C16 by construction, not by assertion.
- **A3.** "Multi-part decision" is a single record with independently addressable parts. If the SUT only models independent records, parts are mapped 1:1 to records plus a container relation, and the container-level archive in T11 becomes "archive all three", which must still leave part authority states untouched.
- **A4.** Archival is a lifecycle fact about the record (replicated), not a per-viewer UI preference. See open question Q5 — if the SUT declares it per-store, CP3 is asserted per-store instead and that is recorded as a documented oracle variance, not a silent relaxation.
- **A5.** Revocation is forward-effective and bitemporal: an as-of query before the revocation's effective time still returns the part as applicable-as-of-then. See Q6.
- **A6.** Revocation is *not* redaction. Original bytes, anchors and evidence class survive in the historical view. Erasure semantics belong to C20, not here.
- **A7.** Exactly one repository (`rep_R1`) is in play; the two stores are replicas of the same record set, and repository identity is independent of clone path (two different paths on the two hosts, deliberately).

## 3. Abstract store model (the only surface the oracle asserts over)

- `events(store)` — append-only admitted event list; each entry exposes `event_id`, `payload_digest`, `principal`, `producer`, `origin_host`, `origin_store`, `logical_time`, `type`, `subject`, `anchor`.
- `current(store, scope, as_of=now, include_archived=false)` — set of applicable entries `{part_id, state, evidence_class, authorizes_action, anchor(repo,path,rev,sha), record_version_id, archived}`.
- `history(store, subject)` — complete ordered lifecycle chain per part: every state with authorizing event, principal, effective time, and the anchor/bytes exactly as first recorded.
- `receipts(store, event_id)` — per-peer ladder position in `{local_durable, queued, transferred, remote_received, admitted, materialized, injected, task_acknowledged, unknown, pending_causal, rejected}` plus `last_observed_at`, plus a **rejected ledger** listing refused events with a disposition.

Ladder states are independent (R08). The oracle never asserts *how* any of this is stored.

## 6. Assertions

### K1 — only authorized parts change (CP1)

- **A1.1** `current(S1,'svc/billing/tax/')` and `current(S2,…)` both contain `D2` as `applicable`, `human_ruling`, `authorizes_action=true`, anchor `rev_c2`.
- **A1.2** `history(*,'D1#P2')` shows `superseded_by:D2` at t3 by `usr_juno`, with the original `rev_c1`/`sha256:bbbb2222p2` still retrievable.
- **A1.3 (negative, N4)** `D1#P1` and `D1#P3` are bit-for-bit unchanged at CP1: same `state`, `evidence_class`, `authorizes_action`, `anchor_rev`, `source_sha256`, `record_version_id` as at CP0.
- **A1.4 (negative, N3)** `EV06` is refused. At CP2, `D1#P1` state is `revoked` **by `EV07` only**, `D1#P2` is `superseded_by:D2` only, and no part carries `agt_scribe` as an authorizing principal. The `claimed_actor`/`claimed_active` fields and the `MUST` prose confer nothing.
- **A1.5 (negative, N7)** `EV06` appears in the rejected ledger with an explicit unauthorized disposition; silent discard fails the case as surely as acceptance does.

### K2 — archive is not revoke (CP2 → CP3)

- **A2.1** Between CP2 and CP3 no part's `state`, `evidence_class` or `authorizes_action` changes. The only delta is `archived: false → true` plus default-surfacing behaviour.
- **A2.2** `current(S1,'svc/billing/', include_archived=true)` at CP3 still reports `D1#P1: revoked` and `D1#P3: applicable_provisional` — archival did not collapse the two into one indistinct "inactive" state.
- **A2.3** `D2` (not part of the archived container) is untouched: `applicable`, `archived=false`.
- **A2.4** `history(*,'D1#P1')` distinguishes the t6 `revoked` entry (principal hera, reason recorded) from the t9 `archived` entry, with different event ids and different types.

### K3 — restoration preserves lifecycle (CP4, CP5, CP6)

- **A3.1 (negative, N1)** After `EV11` (unarchive), `D1#P1` is **absent** from `current(S1,'svc/billing/')` and from `current(S1,'svc/billing/invoicing/')`. Unarchive restores visibility of the record, never the revoked authority.
- **A3.2 (negative, N2)** After `EV11`, `D1#P3` is still `model_inference` with `authorizes_action=false`. The fact that a human (hera) performed the restore does not upgrade anything inside the restored record.
- **A3.3 (negative, N5)** No prior event is mutated, deleted, re-identified or re-ordered by `EV09`/`EV11`; restoration is a new appended event. No restored part is re-anchored from `rev_c1` to head `rev_c3`.
- **A3.4** `sto_S2`, rebuilt from the pre-revocation export `EXP_T4`: during the window before reconciliation its view must be labeled `known_cursor=t4, unknown_beyond_cursor`; it must not assert `D1#P1` as authoritative-current unlabeled. After reconciliation (CP5), `D1#P1` is `revoked` — **the backup cannot resurrect it (N6)**.
- **A3.5** At CP5, `events(S2)` contains `EV01, EV03, EV04, EV07, EV09, EV11` exactly once each, with original `event_id`s and `payload_digest`s; nothing acknowledged before t12 is lost by the restore.
- **A3.6** At CP5, `current(S2,'svc/billing/')` is set-identical to `current(S1,'svc/billing/')` at CP4 (both replicas converge).
- **A3.7 (negative, N9)** At CP6, after the materialized current view of `sto_S1` is destroyed and rebuilt from the retained event log, `current(S1,'svc/billing/')` is identical to CP4 and the admitted-event count is unchanged. *(Foundation proof bullet 5: losing the materialized index does not lose acknowledged events.)*
- **A3.8** As-of queries: `current(S1,'svc/billing/invoicing/', as_of='t2')` returns `D1#P1` applicable; `as_of='t12'` returns empty; `history(S1,'D1#P1')` still yields `sha256:aaaa1111p1`.

### K4 — receipts, retries and authority boundaries (CP2, throughout)

- **A4.1** After the lost ack at t7, `receipts(S1,'EV07').to(S2)` is `transferred` or `unknown` — **never** `admitted`. A producer may not claim a remote admission it has not observed.
- **A4.2** After the identical retry at t8, the receipt reconciles to `admitted`, and `events(S2)` contains exactly **one** `decision.revoke_part` on `D1#P1`. Zero duplicate semantic effects (R07).
- **A4.3 (negative, N8)** No receipt at `admitted`/`materialized` is reported anywhere as task acceptance, qualification, merge or human authorization. *(Foundation proof bullet 3.)*
- **A4.4 (negative, N10)** Plans A, B and C yield identical `current` and `history` at the final checkpoint. Under plan B, every event whose causal prerequisite has not yet arrived sits in `pending_causal` — visible, neither applied nor discarded.

### Positive controls

- **PC1 (`EV04`, CP1)** — the authorized narrow partial supersession **must succeed**. A SUT that passes every negative by refusing all writes fails here.
- **PC2 (`EV14`, CP7)** — after archive → unarchive → store restore → index rebuild, an authorized in-scope human ruling is still admitted and supersedes the provisional `D1#P3`. This also proves that a provisional part is retired only by an explicit authorized act, never as a side effect of restoration. At CP7: `D4` applicable/authorizing, `D1#P3` `superseded_by:D4` and out of the applicable view, `D1#P1` still revoked.

## 7. Pass / fail

**Pass** requires every assertion in §6 to hold under all three delivery plans, with the SUT's declared observable mapping fixed before the run.

**Immediate rejection** (per the go/no-go list — authority-changing error, silent loss, fabricated authority):

1. `D1#P1` applicable at or after CP4 in any view not explicitly labeled historical/as-of.
2. `D1#P3` presented as authorizing an action at any checkpoint.
3. `EV06` applied in whole or in part, or accepted on the strength of its own claimed fields.
4. Any acknowledged event missing from `events(store)` at CP5 or CP6.
5. Any state change to a part outside the authorizing event's scope.

No latency or token result offsets any of these.

## 8. Oracle-change protocol

Expected outcomes above are frozen. A change requires a written source/requirement reason citing the specific line of `requirements.md` or `acceptance-cases.md` that compels it; both the original and corrected expectation are retained in the record, and the original measured result is reported alongside any revision. Ambiguities are resolved by declaring the SUT's answer to the open questions **before** the run, not by relaxing an assertion after a failure.

## 9. Deliberately not asserted

Storage engine, file layout, event schema, ID format, transport, index technology, whether archive is a flag or a separate collection, and whether parts are rows or documents. C16 constrains observable lifecycle semantics only — these are declared design choices (`requirements.md` §"Non-negotiable versus design choice").
