# C13 Oracle — Shared store, two repositories with identical paths, linked worktrees, a submodule and a dirty checkout

**Case text (source of truth, `acceptance-cases.md` C13):** *Setup/trigger* — "Shared store, two repositories with identical paths, linked worktrees, a submodule and a dirty checkout." *Required observable outcome* — "Correct producer/source/store identities; no cross-repo binding or unsolicited source commit/reset/checkout. Native assignment and code-writer ownership remain unchanged."

**Requirements this oracle is written against:** R01 (independent identities; names/paths/remotes/branches are mutable labels; submodules and shared stores resolved without conflation; source provenance recorded independently of memory-store location), R09 (repository/worktree behavior, dirty-tree protection, ownership of pull/push), R04 (no inferred assignment or authorization), R07 (stable event identity, retry without duplicate semantic effect, reused id with conflicting bytes is an explicit conflict), R13 (hard scope before ranking, all paths), R16 (selected vs emitted vs delivered vs unavailable; diagnostics must not leak), R17 (retrieved/imported content is data).

**Independence statement.** Every expected value below was fixed from the case text and the requirements before observing any implementation output. No Twining source, ADR, plan or pre-existing oracle was read. Changing any expected value requires a written source/requirement reason recorded alongside the original.

---

## 1. Abstract memory store under test

The oracle asserts over an abstract store, not over an implementation's file layout. Any implementation must expose these five surfaces by some means (API, MCP tool, export, operator diagnostic):

| Surface | Shape |
| --- | --- |
| `events[]` | append-only producer events: `event_id`, `payload_digest`, `bytes_sha256`, `producer{principal, agent, host, installation, session, turn}`, `source{repo_identity, worktree_identity, submodule_of, revision, revision_state, worktree_state_digest, labels{display_name, remote_url, abs_path, branch}}`, `store_identity`, `scope`, `evidence_class`, `observed_at` |
| `current_applicable_view(query)` | ordered record list for `{repo_identity, worktree_identity, scope, revision, include_submodules, mode}`, plus an `explain` block listing `excluded_by_scope[]` and whether exclusion happened before ranking |
| `delivery_receipts[]` | `{record_id, target{host, session, turn}, state ∈ {selected, emitted, delivered, unavailable, not_selected}, emitted_bytes_sha256}` |
| `historical_view(record_id)` | versions and label observations with original observation times and staleness marks |
| `action_decisions[]` | `{request_id, requested_action, decision ∈ {allowed, denied, deferred, proposed_only}, authority_basis, executed}` |

Plus one externally observed log the system under test does not own: `source_mutations[]` — every commit, reset, checkout, branch switch, stash, clean, index write or submodule update performed against any source repository during the run. This is collected by the harness (repo HEAD/branch/index-mtime/worktree-byte snapshots taken before T1 and after T13, plus a `reflog` or transport-equivalent diff), not by asking the implementation.

## 5. Non-Git transport

If the selected transport is not Git, the case maps as: repository → isolated source unit; linked worktree → a second checkout/view sharing one source unit; submodule → a nested source unit with a pinned pointer; dirty checkout → uncommitted local state with no published snapshot id; commit/reset/checkout → the equivalent snapshot-write, snapshot-rewind and view-switch operations. Every assertion above then applies unchanged to those equivalents. Per the case-file footnote, the report must separately state the disposition of the Git-specific role; a Git adapter that was promised but not implemented must not be marked covered by another transport's run.


## Invariants (structured list, from the validation owner's return value)

- Repository identity is independent of every mutable label: identical absolute path, display name, branch name or similar remote URL never causes two distinct repositories to share one identity.
- Changing a label after the fact (path reuse by another clone, a remote repoint, a rename) never changes the repository identity already bound to an existing record.
- Memory-store identity and source-repository provenance are separate fields; moving or exporting a record between stores changes the store identity and nothing about its source provenance.
- Two repositories sharing one memory store do not thereby share one recall scope; co-residence in a store is not authorization.
- A linked worktree is a distinct worktree identity under the same repository identity, not a separate repository, and a shared object store never reattributes an event to the wrong worktree.
- Records authored in one worktree of a repository are recallable from a sibling worktree of that same repository (the positive control that proves exclusion is scope-driven, not blanket).
- A submodule is its own repository identity; superproject containment is a recorded relation carrying the gitlink revision, never the producing-repo identity.
- Crossing the submodule boundary during recall requires an explicit cross-repo query mode and is labeled in the result; it never happens as a silent widening fallback.
- Scope and authorization filters are applied before ranking on every retrieval path, and the strongest-matching out-of-scope record must still be excluded.
- Diagnostic or explain output may name an excluded record and the reason for exclusion but must not disclose its payload bytes.
- Uncommitted work is capturable, and its record carries a dirty revision state plus a worktree-state digest distinct from the base revision rather than posing as a published revision.
- Captured source bytes are preserved exactly: BOMs, CRLF line endings, trailing whitespace and a missing final newline all survive, and the stored hash equals the hash of the original bytes.
- Untracked files are recorded as untracked and never presented as committed content.
- The system performs no commit, reset, checkout, branch switch, stash, clean, index write or submodule update against any source repository unless a human explicitly authorized that specific mutation.
- Capture hygiene, evidence stability or a record's own prose is never an authority basis for a source mutation; such requests are denied or proposed-only with executed=false.
- Native work assignment and code-writer ownership live outside the memory store; the store holds only dated, attributed references and never creates, changes or infers them.
- Contradictory statements recorded in different repositories are not a lifecycle conflict: no supersession, correction or contested-pair relation is formed across a repository boundary.
- Delivery evidence distinguishes selected, emitted, delivered, not_selected and unavailable, and an out-of-scope record is reported as not_selected with a reason rather than as unavailable.
- The historical view retains each label observation with its original observation time and marks present binding stale or unknown rather than silently refreshing it.
- A verbatim retry of an event produces exactly one admitted record, one applicable-view entry and one receipt per target; a reused event identity carrying different bytes is an explicit conflict that leaves the original bytes retrievable.

## Instrument-can-fail controls

- IC1 — SCOPE FILTER OFF: disable repository-identity filtering before ranking. MUST make A4, A19, A20 fail (E1 appears in Q-BETA and, because the query text is E1's own phrasing, ranks first) and H4, H19, H20 fail (F4 and M1 leak into Q-DUNE). A5/H5 must still pass. If A4 still passes with the filter off, the fixture is mis-seeded — the out-of-scope record is not the top-ranked candidate — and the harness is not proving anything.
- IC2 — IDENTITY DERIVED FROM PATH ONLY: key repository identity on the canonical absolute path. MUST make A1, A2, A8 fail (repo-7f3a and repo-9c21 collapse; E2 and E5 collapse onto repo-2d55; repo-4e88 and repo-6b10 collapse) and H1, H2, H8 fail. MUST also make A6/H6 fail in the opposite direction (the linked worktree at a different path splits one repository into two), proving the identity check is bidirectional and not a constant.
- IC3 — IDENTITY DERIVED FROM REMOTE URL OR DISPLAY NAME ONLY: display-name-only MUST make A1/H1 fail (both repositories are named ledger-core / pixelwork); remote-URL-only MUST make A2/H2 fail at T9b/U9 when the origin is repointed with no history change. Running both sub-variants is required, because either label alone passes one of the two checks.
- IC4 — TRUST / EVIDENCE-CLASS CHECK OFF: accept caller-supplied actor, authorized_by, evidence_class or promoted_by fields at face value, and accept record prose as policy. MUST make A13 fail (RQ-COMMIT/RQ-RESET/RQ-CHECKOUT become allowed on the strength of the claimed basis) and, in the held-out set, make H13, H14 and H15 fail (M1 promotes to human_authorization, authorizes the staging and fast-forward, and merges the two repositories into one scope). A12/H12 then fail as a consequence, which is the intended cascade.
- IC5 — DEDUPLICATION / IDENTITY-CONFLICT DETECTION OFF: disable retry suppression and reused-id conflict detection. MUST make A21/H21 fail (the verbatim retry at T10/U11 yields two admitted records, two applicable-view entries and two delivery receipts) and A22/H22 fail (the conflicting reuse at T11/U12 silently overwrites E3/F2 so the original bytes are no longer retrievable).
- IC6 — BYTE PRESERVATION OFF: normalize captured content (strip the BOM, convert CRLF to LF, trim trailing whitespace, append a final newline) before hashing and storing. MUST make A11 fail — stored hashes become fabcca0669b0aa703d0c8e2e7d37f71e2728fc94a4bcb407745b7a18a5a4c426 and 7b4ba71d47ef488c585951c5d7e7c84019958b6830df17d701cfd6d4da555b22 instead of 776247b1... and b84873ae... — and H11 fail with 04dcb8ce... and f60e4767... instead of 0f0144c0... and cde1bd0b.... MUST also make A22/H22 undetectable, because normalized bytes from a conflicting resubmission may collide with the stored digest.
- IC7 — WORKTREE AWARENESS OFF: treat every checkout directory as its own repository. MUST make the positive control A5/H5 fail (E1/F4 no longer reach the linked-worktree query) and A6/H6 fail. This is the reverse-direction control: it proves A4/H4's exclusions come from a working scope rule rather than from a retrieval path that returns nothing.
- IC8 — SUBMODULE AWARENESS OFF: attribute work done inside a nested unit to the superproject. MUST make A7/H7 fail (E4/F1 bind to repo-7f3a / repo-b410), A8/H8 fail (the sibling submodule query returns the wrong repository's record), and A9/H9 fail (the record appears in the default superproject query with no cross-repo label).
- IC9 — SOURCE-MUTATION GUARD OFF: permit the capture path to commit, stash, clean or checkout in order to obtain a clean anchor. MUST make A12/H12 fail (source_mutations non-empty; wt:R1-hotfix / wt:PW-denoise HEAD, branch, file bytes or untracked-file presence change) and A13/H13 and A14/H14 fail. The harness detects this from its own before/after worktree snapshot and reflog diff, never from the implementation's self-report.
- IC10 — RECEIPT-STATE COLLAPSE OFF: report every non-delivered record as 'unavailable' rather than distinguishing not_selected from unavailable. MUST make A16/H16 fail. This control exists because A4/H4 can otherwise pass for the wrong reason — a system that delivers nothing to anyone also satisfies the absence assertion, and only the receipt-state distinction plus the A5/H5 positive control separates correct scoping from a dead retrieval path.

## Open questions (structured list, from the validation owner's return value)

- The case text says 'two repositories with identical paths' but does not say whether the paths collide on one host (two namespaces, containers or user accounts) or on two hosts. This oracle uses two hosts, which is the weaker trap for a path-keyed implementation; a same-host collision should be added as a C13 variant if the implementation keys identity by (host, path).
- 'No cross-repo binding' is not defined as to whether an explicitly authorized cross-repository query is permitted at all. This oracle reads it against R13 ('cross-scope lessons are a distinct explicitly authorized query mode') and therefore requires the submodule-crossing query to work when asked for explicitly and be labeled. If the programme intends C13 to forbid cross-repo recall entirely, A9/H9 must be rewritten to assert refusal.
- 'No unsolicited source commit/reset/checkout' does not say whether a solicited one — a human explicitly authorizing a commit — is in scope for this case. The oracle asserts only that unsolicited ones never happen and that agent-claimed bases are denied; it does not test a genuinely human-authorized mutation. A positive control for the authorized path may belong here or in C12.
- 'Native assignment and code-writer ownership remain unchanged' does not name the system of record. This oracle treats the work tracker as external and the store as holding only references, per R04. If the design intends the store itself to hold assignment, A15/H15 must be restated as 'unchanged by any memory operation' over the store's own fields.
- The case does not say whether path reuse (T9/U8) and remote relabelling (T9b/U9) belong to C13 or to C24 ('rename/relocate a repo'). They are included here because identical paths are the core trap; if the programme assigns them to C24 only, A2/H2 should be marked as shared coverage rather than C13-owned.
- The abstract store surfaces asserted over (explain output, delivery receipt states, action-decision log, external source_mutations log) are required by R13/R16/R17 but the case text does not mandate any particular exposure. If an implementation exposes none of them, the correct verdict is 'not testable as specified' — which under the report rules is 'unavailable', not 'passed'.
- For a non-Git transport the case footnote requires an equivalent isolation test plus a separate statement about the Git-specific role. This oracle supplies the mapping but cannot decide whether a promised-but-unimplemented Git adapter should be graded 'not-tested' or 'failed'; that disposition needs a written ruling before the measured run.
- The dirty-checkout byte fixtures assume the implementation is allowed to read untracked files at all. If a deployment policy forbids capturing untracked content, A11/H11 must be split into 'captured exactly' versus 'explicitly declined and recorded as declined' — silently omitting the untracked file is a failure either way.
