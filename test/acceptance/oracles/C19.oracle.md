# C19 Oracle — Revoke user/source access while a replica is offline or a result is cached

**Source of truth:** `acceptance-cases.md` C19 row; `requirements.md` R08, R12, R18 (with R03/R04/R13/R16/R17 touched by the trigger sequence); `05-verification-and-operations.md` test-design section.
**Derivation rule:** every expected outcome below is derived only from those three documents plus the fixture-declared policy. No implementation, ADR, plan or existing oracle was consulted.

## 1. Abstract model under test

The oracle asserts over five surfaces, which must be separately observable (R08 requires local persistence, queued transfer, receipt, admission, materialization and context inclusion to be modelled independently):

| Key | Surface | Meaning |
| --- | --- | --- |
| **EV** | events / records | immutable event log + stored record bodies, identities, digests, evidence classes |
| **CV** | current applicable view | what a given principal on a given host is served *now* |
| **DR** | delivery / receipt states | per-host per-event: queued / delivered / admitted / acknowledged; per-packet emission and delivery |
| **HV** | historical view | what was true and what was served earlier, including last-known source facts with original observation times |
| **AQ** | action-qualification decisions | `qualified` / `denied(reason)` / `deferred(reason)` for a named action, with the evidence cited |

Any implementation that cannot expose these five separately fails C19 by construction, not by assertion.

## 3. Declared policy (fixture-supplied, not implementation-supplied)

`P-OFFLINE-READ-V1` — offline reads of already-replicated records are **allowed but labelled** (`permission_epoch`, `epoch_as_of`, `freshness=unverified_offline`, `staleness_seconds`); beyond **900 s** of permission staleness the read is **denied** (`permission_epoch_stale`); staleness is measured from the issuing authority's stamp on the last applied epoch, never from replica wall clock; offline action-qualification is **deferred**, never qualified; a cached result is **refused and invalidated** once the revocation is known; source state with a revoked source credential is **unknown**, with the last-known fact retained and marked stale; revocation restricts serving and is **not** deletion, retraction or redaction.

The policy is part of the fixture precisely so that C19 tests *enforcement of a declared policy*, not agreement with one particular default. The held-out variant declares a deliberately different policy.

## 5. Required observable outcome — assertions

### EV — events and records

- **A01 (EV)** `evt-REV-0001` exists with a stable identity, digest `sha256:dd04dd04dd04dd04`, epoch `pe-5`, evidence class `authenticated_human_authorization`, and both sub-revocations (user read, service source credential) represented as **separate** revoked grants.
- **A02 (EV, dedup)** The byte-identical redelivery at T8 produces **exactly one** semantic revocation effect: one lifecycle transition, one epoch, a second *receipt* recorded and marked duplicate. No second revocation record, no re-fired state change.
- **A03 (EV, ordering)** The out-of-order `evt-GRANT-pe4` replay at T8 is admitted into the log and labelled `stale_epoch_superseded_by_pe-5`, with **zero** effect on the applicable view. Arrival order does not settle authority (R05).
- **A04 (EV, byte preservation)** At T13 `rec-QL-101` still has `sha256:1f2a7c93be04d55a`, 4182 bytes, `utf-8/LF`, identical to the T1 manifest; lifecycle state is `access_revoked`, and `deleted`, `redacted`, `superseded` are all false. Revocation is a serving restriction, not a deletion (C20 owns deletion).

### CV — current applicable view

- **A05 (CV, NEGATIVE — primary)** After T5, for `u_marisol.vane` on host-ALDER, **no** path returns `rec-QL-101`'s body bytes, source hash, source URI, anchor, title, revision or any snippet of it: exact-ID fetch, lexical query, semantic query, graph-neighbour expansion from `rec-BA-777`, cached diagnostics, operator diagnostics dump, and error/log text are all covered. A denial may echo the identifier the caller already supplied; it may add nothing else. Authorization is applied **before** ranking and expansion (R13).
- **A06 (CV, positive control)** At T6b teodor's exact-ID fetch of `rec-QL-101` on ALDER **succeeds** and returns bytes matching the seeded hash. Revocation is principal-scoped; a blanket outage is a failure, not a pass.
- **A07 (CV, positive control)** At T6c marisol's fetches of `rec-BA-777` and `rec-BA-781` succeed on **both** ALDER and BIRCH. Revocation of one scope does not degrade a neighbouring scope (R06).
- **A08 (CV, offline, within budget)** At T7 on BIRCH the read is **allowed** per the declared policy and the response carries `permission_epoch=pe-4`, `epoch_as_of=T0`, `freshness=unverified_offline`, `staleness_seconds=300`. The response contains **no** assertion that access is current, verified, or checked, and BIRCH makes no statement about `pe-5`.
- **A09 (CV, offline, budget exceeded)** At T10 the same read is **denied** with reason `permission_epoch_stale`. The 1500 s figure is computed from the issuing authority's epoch stamp; BIRCH's +30 min local clock skew must not change the decision boundary in either direction.
- **A10 (CV, cache)** At T6 on CEDAR the replay of `pkt-A1` / read of `cacheentry-77` is **refused** with `cache_entry_invalidated_by_revocation`, and the cache entry's state is `invalidated` as of T5. A cached materialization is not a permission.
- **A11 (CV, trust boundary — NEGATIVE)** `rec-BA-781` is readable by marisol (allowed scope) yet the applicable view for `svc/ledger/` remains revoked at `pe-5`; the record is rendered with evidence class `reported_unverified`, appears in **no** authorization derivation, and its text confers no rights. Imported content is data, not policy (R17, R03).
- **A12 (CV, no silent widening — NEGATIVE)** Graph expansion from `rec-BA-777` along the cross-scope `related_to` edge stops at the `svc/ledger/` boundary for marisol, and no cross-scope lesson mode is silently entered as a fallback.

### DR — delivery and receipt states

- **A13 (DR, NEGATIVE — honesty about offline knowledge)** Between T5 and T12, the receipt state of `evt-REV-0001` at host-BIRCH is `queued_undelivered`; **no** surface on any host — status, dashboard, diagnostics, packet trace or prose answer — states or implies that BIRCH has received, applied or is enforcing `pe-5`. ALDER and CEDAR show `admitted+acknowledged` at 09:16:00Z.
- **A14 (DR, packet)** `pkt-A1` remains recorded as `delivered` at T2 to `sess-CED-1` with `emitted_bytes_hash sha256:cc03cc03cc03cc03`; the delivered/emitted/selected distinction is preserved (R16) and the delivery record is not converted into an undelivered one to make the revocation look tidy.
- **A15 (DR, reconnect)** At T12 BIRCH applies `evt-REV-0001` **exactly once**, advances its cursor past it, and invalidates local `svc/ledger/` cached results. At T13 marisol's read on BIRCH is `denied:scope_read_revoked`.

### HV — historical view

- **A16 (HV)** The T2 delivery of `pkt-A1` is retained verbatim with its `pe-4` context: not deleted, not rewritten, and **not re-servable**. History is preserved; serving is not.
- **A17 (HV, NEGATIVE — no retroactive knowledge)** BIRCH's T7 read is retained as `served_under_epoch_pe-4`; it is **not** retroactively relabelled as a policy violation, and **no** record asserts BIRCH knew `pe-5` before 09:50:00Z.
- **A18 (HV, source freshness)** `repo/quartz-ledger`'s last-known head remains `r-9f31a2` with `observed_at 09:05:00Z`, marked stale, and present state is reported **unknown**. The true head `r-c7d410` is never produced, guessed or inferred (R12; mirrors C01's "source unavailable means current state unknown").

### AQ — action-qualification decisions

- **A19 (AQ)** At T11: `qualify_acceptance(svc/ledger/, marisol)` is `denied:scope_read_revoked` on ALDER and CEDAR, and `deferred:permission_epoch_unverified` on BIRCH — **never** `qualified` anywhere. `export_scope_bundle(svc/ledger/)` is denied on all three.
- **A20 (AQ, source)** `publish_source_summary(repo/quartz-ledger)` is `denied:source_inaccessible`; the decision explicitly reports current head unknown and does **not** fall back to `r-9f31a2` as if current.
- **A21 (AQ, positive control)** `publish_source_summary(repo/basalt-atlas)` is `qualified`, with a live head check returning `r-2ab55e` verified at 09:24:00Z. The revocation of one source credential does not disable the freshness path for another.
- **A22 (AQ, NEGATIVE — evidence provenance)** No qualification decision anywhere in the run cites `pkt-A1`, `cacheentry-77` or `rec-BA-781` as supporting evidence.

## 6. Pass condition

All of A01–A22 hold, **and** every instrument control in `instrument_controls` demonstrably flips its named assertion to FAIL when its switch is disabled. A run in which every assertion passes but no instrument control can be made to fail is reported as **not tested**, never as passed.


## Invariants (structured list, from the validation owner's return value)

- INV-1 Knowledge honesty: a replica's enforcement state is a function only of permission events it has actually received, and no surface anywhere may state or imply that a replica has applied an event whose receipt state is still queued or undelivered.
- INV-2 Epoch monotonicity: once a higher permission epoch is applied at a replica, redelivery or out-of-order replay of a lower epoch is recorded as a stale duplicate and produces no grant, regardless of arrival order or drain order.
- INV-3 Revocation idempotence: byte-identical redelivery of a revocation event yields exactly one semantic effect and one additional receipt, never a second lifecycle transition.
- INV-4 Cache subordination: a cached or previously materialized result confers no authorization; once a revocation is known at the host, the cached entry is invalidated and refused to the affected principal while remaining servable to unaffected principals.
- INV-5 Delivery irreversibility: a packet already delivered to a session stays recorded as delivered with its original emitted-bytes hash; revocation never rewrites delivery history into non-delivery.
- INV-6 Revocation is not deletion: stored source bytes, hash, byte length and encoding of a record in a revoked scope are unchanged after revocation, and the record is not marked deleted, redacted or superseded.
- INV-7 Pre-ranking authorization: every retrieval path - exact ID, lexical, semantic, graph expansion, cache, operator diagnostics and error text - applies the current permission epoch before ranking or exposure, and a denial discloses nothing beyond the identifier the caller already supplied.
- INV-8 Narrow blast radius: revocation of one principal's rights in one scope leaves every other principal's rights and every other scope exactly as they were, verified by an explicit positive control in each run.
- INV-9 Source unavailability yields unknown: when a source credential is revoked, current source state is reported unknown, the last-known revision is retained with its original observation time and marked stale, and the stale revision is never presented as current.
- INV-10 Offline action gating: while a replica cannot confirm its permission epoch, no consequential action is qualified on that replica; the declared policy's offline decision (defer or deny) is applied literally and is never auto-promoted to qualified on reconnect.
- INV-11 Clock independence: permission staleness and confirmation windows are computed from the issuing authority's epoch stamp, so injected replica clock skew in either direction cannot move an allow/deny boundary.
- INV-12 Data is not policy: imported or replicated prose asserting that access was restored is classed as reported and unverified, is absent from every authorization derivation and qualification rationale, and cannot alter the applicable permission view.
- INV-13 Policy is declared, not assumed: offline and cached-read behavior conforms to the policy supplied with the fixture, so two runs with different declared policies must produce correspondingly different allow/deny outcomes on the same trigger sequence.
- INV-14 Audit non-revision: reads that occurred under an earlier epoch are retained as served-under-that-epoch and are neither erased nor retroactively relabelled as violations or as revocation-aware.

## Instrument-can-fail controls

- Scope filter off: disable the permission-epoch predicate in the retrieval layer (all paths) while leaving response labels intact. A05 (dev) / H05 (held-out) MUST fail by returning rec-QL-101 / rec-CR-214 to the revoked user on the online host. If A05 still passes, the assertion is inspecting a rendered label rather than the served payload and is invalid.
- Scope filter off, exact-ID path only: leave semantic and lexical gating on but bypass the check on direct-by-ID fetch and on the operator diagnostics dump. A05/H05 MUST fail on those two sub-paths specifically. A run where only the semantic path is instrumented will show a false pass here.
- Trust check off: allow reported_unverified content to contribute to the permission derivation. A11/H11 MUST fail - rec-BA-781 / rec-SI-534 restores the revoked scope and a qualification cites it. If the view stays revoked, the assertion is not actually reading the derivation inputs.
- Dedup off: disable event deduplication by digest. A02/H02 MUST fail with two revocation records or two lifecycle transitions; the receipt count and the effect count must be observed separately, since a test that counts only receipts cannot detect this.
- Epoch monotonicity off: accept the replayed older grant epoch on its arrival order. A03 (dev, replay after revocation on the online host) and H03 (held-out, replay drained BEFORE the revocation on the reconnecting node) MUST both fail by re-granting access. Passing one and not the other means order-sensitivity is untested.
- Byte preservation off: normalize, redact or truncate the revoked record's stored bytes on revocation. A04/H04 MUST fail on hash mismatch, byte-length mismatch, or CRLF-to-LF conversion in the held-out record. A hash-only check that omits encoding will not catch the held-out case.
- Freshness labelling off: strip permission_epoch/epoch_as_of/freshness/staleness from offline responses, or stamp freshness=verified. A08/H10 MUST fail. This is the control that proves the offline-honesty assertion inspects the response envelope rather than merely the allow/deny bit.
- Offline-knowledge honesty off: have the coordinator report the queued revocation as enforced on the disconnected replica (optimistic status projection). A13/H13 MUST fail. Verify from the offline replica's own receipt state and from the operator status surface independently - a single-surface check can miss this.
- Cache invalidation off: keep the warmed entry servable after the revocation is admitted. A10 (dev) MUST fail; H07 (held-out) MUST fail for ingrid while still passing for pavel, which additionally proves the invalidation is per-principal and not a blanket cache flush.
- Clock authority off: compute staleness from replica local wall clock instead of the issuing authority's epoch stamp. With the seeded skew (+30 min dev, -25 min held-out) A09 MUST flip to allow and H10 MUST flip to deny. If neither flips, the skew is not reaching the code path under test.
- Source-freshness fallback on: permit the last-known head to be returned as current when the source is inaccessible. A18/A20 and H17/H19 MUST fail by presenting r-9f31a2 / r-4b8e07 as current state. A test that only checks the decision verdict and not the cited head value will false-pass.
- Offline action gate off: allow offline qualification to resolve to qualified, or auto-promote a deferred decision on reconnect. A19/H18 and H15 MUST fail. Assert the decision value at the offline moment AND after reconnect; checking only the post-reconnect state hides the auto-promotion path.
- Positive-control sabotage (fail-open check on the controls themselves): revoke teodor's / pavel's grant, or the retained source credential, without changing anything else. A06, A07, A21 (dev) and H06, H08, H20 (held-out) MUST fail. If the positive controls keep passing, they are not actually exercising the authorization path and every negative assertion in the run is uninterpretable.

## Open questions (structured list, from the validation owner's return value)

- The case says 'enforce the declared offline/read policy' but does not say where that policy is declared or which copy wins when a replica's local policy and the policy carried with the revocation disagree. The oracle resolves this by making the policy a fixture input and asserting literal conformance; if the system instead treats policy as replica-local configuration, the authority-precedence rule needs a documented answer before the run.
- 'Refuse inaccessible serving' does not say whether existence may be disclosed. The oracle permits a denial to echo an identifier the caller already supplied but forbids adding title, URI, anchor, revision, hash or body. If existence disclosure is itself considered cross-scope disclosure, assertion A05/H05 must be tightened to require an indistinguishable not-found response, which is a different and stronger contract.
- The case is silent on derived artifacts: whether revocation must also purge or re-gate embeddings, summaries, extracted graph nodes and rerank caches that were computed from the revoked bytes. The oracle asserts that no path serves them, not that the derived data is deleted; deletion semantics belong to C20 but the boundary between the two cases is not drawn in the text.
- No staleness threshold, confirmation window or grace period is specified for an offline replica. The oracle declares 900 s (dev) and 2700 s (held-out) so that the boundary is testable, but the real deployment values are an agreement item that must be fixed before the measured run per the go/no-go rules.
- Whether an already-delivered packet must be recalled or expired from a receiving turn's context is not addressed. The oracle asserts only that it is not re-served and that its delivery record is preserved; if recall from a live context window is expected, that is an additional requirement on the host adapter (R10/R16) and needs its own assertion.
- The case does not say whether revocation knowledge itself is scope-sensitive metadata - that is, whether a replica may be told 'a permission event for scope X is pending' without being told its content. The held-out policy depends on exactly that signal; if pending-event visibility is itself restricted, the held-out offline branch H09 needs a different denial reason.
- Retry and backoff behavior for requalifying a source whose credential was revoked is unspecified: whether the system should keep probing, how often, and whether repeated denials must be rate-limited or surfaced as an operator alert under R20.
- The case does not state whether the service-credential revocation and the human read revocation must be independently representable or may be modelled as one access change. The oracle asserts independence (H01) on the strength of R01's separate-identities requirement, but the acceptance text alone does not force it.
