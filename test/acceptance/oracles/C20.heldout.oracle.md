# C20 Held-out variant — H20 "billing proration"

Structurally the same case as the C20 development oracle; every name, host, store, revision, wording and the operation ordering differ. Run only after the development set has been used for debugging, and never share fixtures or stores between the two.

## Differences from the development variant (deliberate)

1. Purge happens **before** the redaction, not after.
2. The unauthorized lifecycle attempt is an attempted **redaction** by a contributor (not an attempted purge).
3. The backup restore happens **before** the replica reconnects.
4. The restored backup carries its own self-describing `status: applicable` flag on the old version — a second resurrection vector absent from the development set.
5. The reconnecting replica carries a plausible ordinary runbook note; it does not announce that it is a test, an injection or false, and its surface form is indistinguishable from legitimate contributor prose.
6. Two lifecycle operations arrive out of causal order (the replacement version arrives before the redaction that motivated it).

Identical to the development oracle: all of H-A1 … H-E3 must hold and every instrument control must produce its named failure.
