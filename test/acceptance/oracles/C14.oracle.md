# C14 Acceptance Oracle — ref rewind / snapshot rewind

**Case text (authoritative):** "Git ref checkout/reset/rebase/force-push/cherry-pick, or equivalent exchange snapshot rewind → No silent loss/resurrection of admitted current lifecycle state. Historical view and intentional restoration are explicit. Equivalent events retain their identity across transport representation changes."

**Requirements under test:** primary R05, R09, R12, R19; secondary R02, R03, R04, R07, R08, R16.
**Foundation proof bullets exercised:** "a lower-authority inference cannot supersede the ruling"; "exchange acknowledgements do not become task acceptance"; "changed source revisions invalidate current-use claims without erasing historical records"; "losing the materialized database/index does not lose acknowledged source events".

**Provenance discipline:** this oracle was written from `acceptance-cases.md`, `requirements.md` and the "Required proof before broad implementation" section of `01-foundation.md` only. No Twining source, design doc or plan was read. Expected outcomes are therefore not derived from the implementation under test. Any change to this oracle requires a written source/requirement reason and preserves the original text (oracle_version bump, original retained).

## 1. Abstract store model and required read surfaces

The implementation may store anything it likes; to be testable it must expose (or be adapted behind) five read operations. Assertions below are written only against these.

| Surface | Operation | Returns |
| --- | --- | --- |
| Event list | `list_events(store, filter?)` | ordered, immutable event envelopes |
| Current applicable view | `current_view(store, scope, as_of)` | applicable records with lifecycle state, authorizing event, evidence class, qualification |
| Receipts / delivery states | `receipts(store, event_id)` | independent per-destination states |
| Historical view | `history(store, record_id)` | full ordered lifecycle with prior applicability windows |
| Rebuild | `rebuild_from_durable(store)` | reconstructs view + indexes from retained durable evidence only |

**Event envelope fields:** `event_id`, `payload_digest`, `kind`, `record_id`, `scope`, `evidence_class`, `authored_by`, `observed_by`, `producer{host,store,session}`, `source{repo,revision,path,anchor,source_hash}`, `effective_at`, `recorded_at`, `causal_deps[]`, `representations[]`.

**Evidence classes (R03):** `human_authorization`, `verified_observation`, `worker_report`, `model_inference`, `proposal`, `open_question`.

**Receipt states, independent (R08), never collapsible:** `local_durable`, `queued`, `remote_received`, `admitted`, `materialized`, `injected`, `task_ack`.

**Qualification states (R12):** `qualified`, `stale`, `unknown`, `source_unreachable`.

**Lifecycle states (R05):** `applicable`, `superseded`, `revoked`, `archived`, `contested`, `restored_applicable`.

Key modelling decision: `representations[]` is the seam this case turns on. One semantic event has one `event_id` and one `payload_digest`, and zero-or-more transport representations (a git commit + path, an export bundle entry, a snapshot row). A rewrite adds a representation; it never mints an event.

## 6. Assertions by surface

Ids: `A-EV*` event list, `A-CUR*` current view, `A-RCP*` receipts, `A-HIS*` history. Each is anchored to a checkpoint.

### 6.1 Event list

- **A-EV1 (K1–K6):** every `event_id` present at K0 is present in both stores at every later checkpoint, with an unchanged `payload_digest`. Count never decreases.
- **A-EV2 (K1):** the checkout records exactly one new event `ev-010`, `kind: source.checkout`, `evidence_class: verified_observation`, `head: c1aa`. No `record.*` event is produced.
- **A-EV3 (K2):** the reset records `ev-011` (`source.reset`). After index deletion, `rebuild_from_durable(str-alpha)` returns `acknowledged_events_lost: 0` and a `capture_gap` of `none`.
- **A-EV4 (K3):** `ev-003` appears **once** in `str-beta`'s event list and carries two representations — `{c2aa, .exchange/events/ev-003.json, reachable:false}` and `{c2bb, .exchange/v2/events/ev-003.json, reachable:true}`. The old representation is retained, marked unreachable, not deleted.
- **A-EV5 (K3):** the force-push records `ev-012` (`source.history_rewrite`) naming the rewritten pairs; the rewrite itself changes no record lifecycle.
- **A-EV6 (K3–K4):** `ev-004` has `delivery_attempts: 3` (original, post-lost-ack redelivery, cherry-pick re-carry) and `admitted_effects: 1`, `instances_in_event_list: 1`.
- **A-EV7 (K4):** the cherry-pick adds `c4bb` to `ev-004`/`ev-005` representations and creates no new event ids.
- **A-EV8 (K5):** the snapshot rewind records `ev-013` (`store.snapshot_rewind`); after replay `str-beta`'s list is a superset of its K0 list with zero duplicates.
- **A-EV9 (K6):** refused requests `ev-021` and `ev-022` are **recorded as `rejected_request`** with a `reason_class` — refusal is visible, not silent.

### 6.2 Current applicable view

- **A-CUR1 (K1, K2):** `{rec-050: superseded, rec-100: applicable, rec-200: applicable, rec-300: revoked}` — byte-for-byte the K0 projection. A working-tree rewind changes no lifecycle state.
- **A-CUR2 (K2):** the post-rebuild projection equals the pre-reset projection under the canonical field set `(record_id, state, evidence_class, authorizing_event, qualified_as_of, current_qualification)`.
- **A-CUR3 (K3):** lifecycle states unchanged, but qualification moves: `rec-100`, `rec-200`, `rec-300` → `current_qualification: unknown`, `source_revision_reachable: false` (their anchors `c2aa`/`c3aa` are gone); `rec-050` stays `qualified` at `c1aa`, which survived the rebase. Historical facts keep their original times (R12).
- **A-CUR4 (K4):** zero change versus K3. Patch equivalence at `c2bb`/`c4bb` — including the **byte-identical** `settle.ts` at `c2bb` — requalifies nothing.
- **A-CUR5 (K5, offline):** `str-beta` labels its view `incomplete`, reports a known cursor gap, and does not serve it as complete.
- **A-CUR6 (K5, post-replay):** `str-beta` converges to `{rec-050: superseded, rec-100: applicable, rec-200: applicable, rec-300: revoked}`, **identically under all three replay orders** and despite the +37 min skew.
- **A-CUR7 (K6):** `rec-050` is `restored_applicable` authorized by `ev-020`; `rec-100` remains `applicable` and is `qualified_as_of c5bb` via `ev-031`; `rec-200` remains a `model_inference` with `can_authorize_action: false`; `rec-300` remains `revoked`.
- **A-CUR8 (K6):** because `ev-020` restores `rec-050` into a scope where `rec-100` still governs, the pair is surfaced as `contested` (or resolved by an explicitly documented, authorized precedence rule). Silent ordering by arrival time or recency is a failure (R05).
- **A-CUR9 (K6):** `str-alpha` and `str-beta` produce identical canonical projections; `rebuild_from_durable` on each reproduces that projection with `acknowledged_events_lost: 0`.

### 6.3 Receipts / delivery states

- **A-RCP1 (all):** `task_ack` is `none` for every event at every checkpoint. No storage, admission or materialization state is reported as, or promoted into, acceptance (R04).
- **A-RCP2 (K3):** the lost ack for `ev-003` reconciles — final `remote_received: true`, `admitted: true`, `admitted_effects: 1`, `ack_reconciled: true` — without a second admission.
- **A-RCP3 (K2, K5):** after index loss and after snapshot rewind, receipts for previously acknowledged events are recoverable, and any state the store cannot re-establish is reported as `uncertain`, never defaulted to a completed state.
- **A-RCP4 (K6):** `ev-020` and `ev-030` reach `admitted` + `materialized` on both stores with `task_ack: none`.

### 6.4 Historical view

- **A-HIS1 (K6):** `history(rec-050)` = `[created ev-001 @c1aa applicable] → [superseded ev-003 @c2aa] → [restored ev-020 @c5bb, human_authorization]`, with the superseded window's start/end retained.
- **A-HIS2 (K6):** `history(rec-100)` retains the original qualification at `c2aa` with its original observation time alongside the new `c5bb` qualification.
- **A-HIS3 (K6):** `history(rec-300)` shows creation, revocation, and the **refused** restore `ev-021`.
- **A-HIS4 (K6):** `history(rec-200)` shows creation and the **refused** supersede `ev-022`.
- **A-HIS5 (K1–K6):** at every checkpoint the pre-rewind history is queryable and unmodified; rewinding the transport never edits history entries.

## 7. Negative assertions (what must NOT happen)

| Id | Must not happen | Severity |
| --- | --- | --- |
| **N1** | `rec-050` appears applicable at any point before the explicit restoration `ev-020` | immediate rejection |
| **N2** | `rec-300` returns to any applicable state — including after the snapshot rewind or the refused `ev-021` | immediate rejection |
| **N3** | Any K0 `event_id` is absent later, or any `payload_digest` changes | immediate rejection |
| **N4** | A git operation itself emits a `record.create/supersede/revoke/restore/archive` event | high |
| **N5** | `rec-100` is auto-requalified against `c2bb`/`c4bb` from identical patch or identical file bytes, with no fresh recorded observation | high |
| **N6** | Redelivery (3 attempts) or the cherry-pick re-carry produces >1 admitted effect or >1 event-list instance | immediate rejection |
| **N7** | `rec-200` (model_inference) supersedes, weakens or reorders `rec-100` (human_authorization) — or the refusal is silently dropped | immediate rejection |
| **N8** | Offline `str-beta` presents its view as complete, or asserts knowledge of a revocation it has not received | high |
| **N9** | Any receipt state is reported as, or upgraded into, `task_ack` | immediate rejection |
| **N10** | Any unsolicited source-repo write (commit, reset, checkout, push, ref move) in response to a rewind | high |
| **N11** | `ev-020` alters `rec-050`'s evidence class, author, original effective time or original qualification revision | immediate rejection |

N1/N2 are the "no silent resurrection" half of the case; N3/N6 the "no silent loss" half; N7/N9/N11 are the authority-changing conditions in the go/no-go list.

## 8. Positive controls

- **P1 — intentional restoration works.** `ev-020` succeeds: `rec-050` → `restored_applicable`, supersession preserved in history, contradiction with `rec-100` surfaced (A-CUR7, A-CUR8, A-HIS1). Without P1, N1/N2 could be passed by a system that simply never restores anything.
- **P2 — explicit requalification works.** `ev-031` moves `rec-100` to `qualified_as_of c5bb` while the `c2aa` qualification stays retrievable with its original time (A-CUR7, A-HIS2). Without P2, N5 could be passed by a system that marks everything permanently unknown.
- **P3 — the normal pipeline still works.** The ordinary fast-forward `c5bb` carrying `ev-030` admits end-to-end on both stores (`rec-400` applicable in `src/ledger/`, A-RCP4). Without P3, the rewind handling could pass by wedging the exchange.

## 9. Pass / fail

**Pass** requires: all `A-*` assertions hold at their checkpoints; all `N*` hold throughout; all three positive controls succeed; and the K6 canonical projections of `str-alpha` and `str-beta` are identical to each other and to the post-`rebuild_from_durable` projection.

**Immediate rejection** on any of N1, N2, N3, N6, N7, N9, N11 regardless of other results — these are the case's authority-changing / silent-loss conditions. N4, N5, N8, N10 are scored failures that require a documented disposition.

Report denominators explicitly: 15 expected event ids at K6, 4 records in `src/pay/`, 3 replay orders, 3 delivery attempts for `ev-004`.

## 10. Non-Git transport variant

If the implementation under test does not use Git, run the identical case with: T1/T2 → restore the exchange store to an earlier snapshot; T3 → rewrite the exported batch so the same events carry new batch/segment ids; T4 → import under a changed serialization layout; T5 → re-import an old segment alongside the new head. The identity, loss, resurrection, qualification and receipt assertions are unchanged; only the trigger vocabulary changes. Per the case text, the report must separately state the disposition of the Git-specific role and must not mark an unimplemented Git adapter as covered by the alternative transport's run.

## 11. Assumptions this oracle makes (challengeable before the run)

1. The store lives inside the rewound working tree (hardest reading of "silent loss"); the beside-the-repo placement is a documented easier variant, not a substitute.
2. Restoring a human-authored record requires human authorization; an agent-issued restore of `rec-050` would also be a refusal case.
3. Qualification is keyed to exact revision identity, so byte-identical content at a different revision does not requalify.
4. A restored record coexisting with its successor in the same scope is a contradiction to surface, not a state to auto-resolve.


## Invariants (structured list, from the validation owner's return value)

- A rewind of the transport or working tree (checkout, reset, rebase, force-push, cherry-pick, snapshot restore) never changes any record's lifecycle state; it may only add an observation event describing the rewind.
- Every event_id admitted at any checkpoint remains present with an unchanged payload_digest at every later checkpoint in both stores.
- A record that was superseded or revoked before a rewind returns to an applicable state only through a later, separately authorized, explicitly recorded restoration event.
- A restoration preserves the restored record's evidence class, author, original effective time and original qualification revision, and cannot resurrect revoked authority.
- One semantic event has exactly one event_id and payload_digest regardless of how many transport representations (commit ids, paths, batches, snapshots) carry it.
- A rewritten or re-delivered representation is appended to the event's representation list with a reachability flag; the superseded representation is retained, never deleted.
- Repeated delivery of the same event — retry, force-push re-fetch, or cherry-pick re-carry — yields exactly one admitted semantic effect.
- A record's qualification is keyed to exact source revision identity, so an unreachable anchor revision moves current qualification to unknown while the historical qualification and its original observation time are preserved.
- Identical patch content or byte-identical file content at a different revision never requalifies a record without a newly recorded verified observation.
- Losing the materialized index or database loses no acknowledged event: rebuild from durable evidence alone reproduces the same current view.
- A store that knows its cursor is behind labels its current view incomplete and never asserts knowledge of a revocation it has not received.
- No receipt state — local_durable, queued, remote_received, admitted, materialized or injected — is ever reported as or promoted into task acceptance.
- A record whose evidence class is model_inference can never supersede, weaken or reorder a record whose evidence class is human_authorization, and the refusal is recorded rather than dropped.
- Both stores converge to an identical canonical current-view projection independent of replay order and of the +37-minute clock skew between hosts.
- The system performs no unsolicited write to the source repository in response to any rewind.
- A restored record coexisting with its still-applicable successor in the same scope is surfaced as contested or resolved by a documented authorized precedence rule, never ordered silently by arrival time or recency.

## Open questions (structured list, from the validation owner's return value)

- Scope of 'admitted current lifecycle state': does 'admitted' mean admitted at the rewound store specifically, or anywhere in the fabric? This decides whether str-beta must itself retain the events it had admitted before its snapshot rewind, or may lose them locally and merely converge after replay. The oracle asserts the weaker convergence form at K5 but flags the stronger reading as the one an operator will expect.
- Store placement is unspecified by the case text: the oracle deliberately places both stores inside the rewound working tree (.exchange/), which is the hardest reading of 'no silent loss'. If the implementation requires the store to sit outside the repository, that is a different and weaker test and must be reported as such rather than scored as a pass on this fixture.
- Event equality is undefined: is identity carried by a producer-assigned event_id, by a payload digest over canonical bytes, or by both? The oracle requires both to agree. The same-id/different-bytes case is explicitly C24's conflict; the same-bytes/different-id case is unspecified anywhere and needs a ruling.
- The case text says 'equivalent events retain their identity', but git-level patch equivalence and exchange-event equivalence are different things. The oracle rules that a cherry-picked commit re-carrying event bytes IS the same event, while the cherry-picked source revision is NOT the same revision for qualification. Confirm this split before the run.
- Byte-identical content at a rewritten revision (settle.ts is identical at c2aa and c2bb): may the system generate its own verified observation and requalify automatically, or must requalification be externally triggered? R12 favours requiring a live check; the oracle requires a recorded observation event either way but does not settle who may originate it.
- Does 'intentional restoration is explicit' require human authorization, or may an agent restore with a recorded reason? The oracle takes the strict reading (human authorization to restore a human-authored record). If the looser reading is intended, an agent-issued restore of rec-050 becomes a positive rather than a refusal case.
- Force-push retention: must the unreachable git objects c2aa/c3aa themselves be retained (via a retention ref, reflog or backup), or only the events they carried? The oracle requires only event retention and records object retention as unspecified — but an operator restoring source context would need the objects.
- Temporal query depth: must current_view(scope, as_of=<past time>) reproduce the pre-rewind applicable view, or is per-record lifecycle history sufficient? The oracle asserts only per-record history (A-HIS5); a full as-of view is a stronger and arguably intended reading of 'historical view'.
- Precedence when a restored record and its successor are both applicable in one scope: R05 says concurrent equally authoritative contradictions remain visible unless a defined authorized rule resolves them, but no such rule is defined for restore-vs-supersede. The oracle accepts either 'contested' or a documented rule; the programme should name one.
- Clock skew handling is asserted only as order-independence. Whether effective_at from the +37-minute-skewed host must be corrected, annotated, or left as-recorded is unspecified and affects any time-ordered projection.
