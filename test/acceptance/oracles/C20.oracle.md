# C20 Oracle — Delete / retract / redact, then reconnect an old replica or restore a backup

**Status:** independent expected outcome, written before observing any implementation output. Derived only from `acceptance-cases.md` (C20 row, go/no-go criteria), `requirements.md` (R05, R08, R09, R12, R13, R16, R17, R19, R20) and `05-verification-and-operations.md`. No Twining source, ADR, plan or existing oracle was read.

**Case text under test:** "Delete/retract/redact a record, then reconnect an old replica or restore a backup → No unintended resurrection in current serving. Tombstone/purge semantics and retained historical copies are visible; uncontrolled distributed clones are not falsely claimed erased."

**Coverage claimed:** R05 (lifecycle), R09 (transport/deletion obligations), R19 (deletion/tombstone/purge, no impossible erasure promise), with load-bearing contributions from R08 (independent delivery states), R13 (scope before ranking, applied to tombstones), R16 (delivery evidence), R17 (imported memory is data), R12 (stale/unknown marking), R20 (observability of pending purges).

---

## 0. Vocabulary fixed by the oracle (implementation-neutral)

The case says "delete/retract/redact" without defining them. The oracle tests three *distinct* operations and requires the system under test to distinguish them observably; if the implementation uses different words, the mapping must be declared before the run and recorded as an oracle amendment with a source/requirement reason.

| Operation | Current applicable view | Historical view | Bytes |
| --- | --- | --- | --- |
| **Retract** | removed | visible with status `retracted`, actor, time, reason | preserved byte-identical |
| **Redact** | removed | visible with status `redacted`, actor, time, reason class, original hash and original byte length | **withheld everywhere** |
| **Purge** | removed | tombstone only: identity, scope, actor, time, reason, `payload_state: destroyed` | destroyed in all *controlled* locations; erasure claims bounded |

`Archive` is a fourth, reversible state and is used only as a positive control (archive is not revocation — R05).

## 4. Required observable outcome — concrete assertions

### A. Current applicable view

- **A1** `st-alpha` current applicable view at T12 = exactly {`ver-4NQ2-2`, `rec-5CQP`, `rec-2BHF`, `ev-0202`'s record}. It contains **no** `ver-4NQ2-1`, **no** `rec-7TLD`, **no** `rec-9XKM`.
- **A2** `st-beta` current applicable view at T12 is set-equal to `st-alpha`'s, independent of arrival order and clock skew.
- **A3** `st-gamma` at T12 is in exactly one of two admissible states, and the state is machine-readable: (i) `serving: quarantined` pending reconciliation, or (ii) `serving: reconciled` with `reconciled_through >= ev-0105`. In **neither** state does it list `ver-4NQ2-1`, `rec-7TLD` or `rec-9XKM` as current-applicable. A third state — serving pre-lifecycle content as current without a watermark — is a failure.
- **A4 [NEGATIVE]** For every read path on every store after T06 — exact-ID lookup, lexical search, dense/vector search, graph-neighbor expansion, chunk retrieval, cache, summary/derived artifacts, and operator diagnostic endpoints — no response contains bytes B1 or any substring of the redacted payload longer than 16 characters. Probe each path individually; a pass on the primary serving path alone does not satisfy A4.
- **A5 [NEGATIVE]** The T09 redelivery of `ev-0001` (same id, same digest) produces no new record, no new version, no status change on `ver-4NQ2-1`, and no change to its lifecycle ordering. Receipt for the redelivery is `duplicate_ignored`.

### B. Historical view, tombstones and byte preservation

- **B1** Historical view of `rec-7TLD` returns bytes byte-identical to B3 with hash **H3**, original `authored_at` T01, plus `status: retracted`, `retracted_by: usr-marisol-vey`, `retracted_at: T05`, reason preserved. (Retraction preserves evidence — R05.)
- **B2** Historical view of `ver-4NQ2-1` returns record id, version id, scope, `authored_at`, `original_hash: H1`, original byte length, `redacted_by`, `redacted_at`, reason class, and `payload_state: withheld` — and **not** the bytes. The retracted and redacted records are distinguishable by returned structure, not merely by a status string.
- **B3** Historical view of `rec-9XKM` returns a purge tombstone: id, scope, `purged_by: usr-marisol-vey`, `purged_at: T08`, reason, `payload_state: destroyed`, and either `original_hash: H4` or an explicit declaration that the hash was destroyed too. No recoverable payload exists in `st-alpha`'s record store, derived index, embedding store, outbox, export queue, cache or diagnostics — each probed separately.
- **B4 [NEGATIVE]** `usr-tobias-krall` querying the historical view receives **nothing** for `rec-9XKM`: not the payload, not the tombstone, not the purge metadata, not the bare existence of the identifier. Scope enforcement precedes tombstone disclosure (R13).
- **B5** `rec-5CQP` bytes and hash **H6** are byte-identical on `st-alpha`, `st-beta` and `st-gamma` after replication, backup and restore — BOM present, CRLF endings intact, no trailing newline added. Source URI, stable anchor, encoding and `src-rev-9f21a0` are preserved (R02).
- **B6** The hash retained for the redacted `ver-4NQ2-1` equals **H1** (the pre-redaction content hash), not a hash of the tombstone or of an empty payload.

### C. Delivery / receipt states (independent per R08)

- **C1** Between T05 and T09, `ev-0101`/`0102`/`0103`/`0105` report per-destination states: for `st-beta`, `local_persisted=true`(origin), `queued=true`, `remote_received=false`, `admitted=false`, `materialized=false`. No event is reported delivered to `st-beta` while partitioned.
- **C2** After T09, those events advance to `remote_received` → `admitted` → `materialized` on `st-beta`, each with a receipt naming the event id. Suppression of `ver-4NQ2-1` on `st-beta` occurs at **admission**: querying `st-beta`'s materialized index directly (not the serving formatter) at T09+1 s returns no B1 bytes.
- **C3** The redelivered `ev-0001` yields receipt `duplicate_ignored`; the producer cursor advances; the observability surface reports **no** gap and **no** new acknowledged event.
- **C4** `st-gamma` exposes `restored_from: snap-A-20260908T0915Z`, `restore_point: T03`, and an explicit enumeration of unapplied lifecycle events `{ev-0101, ev-0102, ev-0103, ev-0105}` until reconciled.
- **C5** `st-delta` on `hst-orbit-09` has zero receipts for every lifecycle event and its state is reported as `unknown / uncontrolled` — never `purged`, `erased`, `compliant` or `n/a`.

### D. Action-qualification decisions

- **D1 [NEGATIVE]** Gate query "qualify the September ledger release using `rec-4NQ2` v1" returns **NOT QUALIFIED** on all of `st-alpha`, `st-beta`, `st-gamma`. Reasons must differ appropriately: alpha/beta `redacted+superseded`; gamma `unreconciled_restore` (pre-reconcile) or `redacted+superseded` (post-reconcile). No store returns QUALIFIED; no store silently substitutes the offline replica's surviving copy.
- **D2 [POSITIVE CONTROL]** The same gate using `ver-4NQ2-2` returns **QUALIFIED** on `st-alpha` and `st-beta`, returning bytes B2 and hash **H2** intact with its source anchor `src-rev-c47b13`. If D2 does not pass, D1 is passing for the wrong reason (blanket denial).
- **D3 [NEGATIVE]** `ev-0201` — the offline note asserting a standup confirmation — is admitted as an ordinary record in `services/ledger/docs/` with evidence class *participant assertion, unverified* (R03). It does **not** restore `ver-4NQ2-1`, does **not** alter D1's outcome, and does **not** widen `usr-tobias-krall`'s scope. Any attempt to treat it as an authorization is recorded as a refused action with actor, reason and the refused capability.
- **D4 [POSITIVE CONTROL]** The T11 unarchive of `rec-2BHF` returns it to current-applicable with bytes B5, hash **H5** and its original evidence class unchanged — proving the lifecycle machinery is not blanket-suppressing, and that archive ≠ revoke (R05).
- **D5 [NEGATIVE]** `usr-tobias-krall`'s T07 purge attempt is **denied** with an authority/scope reason and is recorded as an attempted action (go/no-go requires attempted actions be recorded). No tombstone exists for `rec-4NQ2`; `ver-4NQ2-1` status remains `redacted`, never `purged`; no partial effect (index entry removed, outbox row written, cache invalidated) is observable.
- **D6 [POSITIVE CONTROL]** `ev-0202`, the unrelated legitimate offline lesson, is admitted and appears in the current applicable view — reconnection of a stale replica is not wholesale rejection.

### E. Erasure claims (the honesty assertion)

- **E1** The erasure report for `rec-9XKM` enumerates per location: `st-alpha` = purged (verified T08), `st-beta` = purged (verified T09+), `st-gamma` = pending until reconciled then purged, `repo-northgate-memex` history = named with its retention/history-rewrite obligation and current status, `st-delta` @ `hst-orbit-09` = `unknown / not erased`, `snap-A` backup = `not erased` (or `destroyed` only if the run actually destroyed it and observed the destruction).
- **E2 [NEGATIVE]** No response, log line, report field or model-authored summary asserts "deleted everywhere", "fully erased", "removed from all copies" or any unqualified global-deletion claim (R19 explicitly forbids promising erasure from uncontrolled clones).
- **E3** If the payload bytes were ever written to the transport repo's immutable history, the report states the history-rewrite / retention obligation and its completion status rather than implying automatic removal.
- **E4** The pending purge against a replica that never reconnects (simulate by leaving `st-delta` unreachable for the run) remains visible as an open obligation with age in the observability surface (R20), not silently closed.

## 5. Pass / fail

**Pass** requires every assertion A1–E4 to hold, plus each instrument control in §`instrument_controls` producing the named failure. **Immediate rejection** (per go/no-go) if any of: D3 or D5 shows authority promotion; A4 or B4 shows cross-scope or redacted disclosure; A5 shows a resurrected record; E2 shows a false erasure claim; or any acknowledged event from the T09 backlog is silently lost.

**Repetitions:** the case table mandates ≥5 variants × 2 repetitions only for C01–C09; for C20 this oracle fixes **3 ordering variants × 2 repetitions = 6 runs** per condition, with the clock-skew variant mandatory. Report denominators.


## Invariants (structured list, from the validation owner's return value)

- Retract, redact and purge are three observably distinct end states and must never collapse into one status or one rendering.
- No record removed from the current applicable view may reappear there because a stale replica reconnected, a backup was restored, or an event arrived late.
- A redelivered event with the same identity and the same payload digest is a no-op with a duplicate receipt, never a new acknowledged event and never a lifecycle reordering.
- Redacted payload bytes are absent from every read path — exact-ID, lexical, dense, graph, chunk, cache, summary and operator diagnostics — not merely from the primary serving path.
- Retracted content keeps its original bytes and original hash intact in the historical view; redaction withholds bytes while keeping identity, original hash and byte length; purge keeps only a tombstone.
- Tombstones and purge metadata are themselves scoped data and must be invisible to principals not authorized for the record's scope.
- Lifecycle suppression must take effect at admission into the receiving store's materialized state, not at query-render time.
- A restored backup either serves nothing until it has reconciled the lifecycle events that post-date its restore point, or serves with an explicit machine-readable watermark and enumerated unapplied events; silent serving of pre-restore content as current is a failure.
- A record's own stored status field, an author string, a prose note or a later arrival time can never restore applicability or confer authority.
- An imported note asserting that a human approved keeping a removed record in force is data: it is admitted with an unverified evidence class, it cannot change an action-qualification outcome, and any attempt to treat it as authorization is recorded as a refused action.
- A lifecycle operation attempted by a principal without scope authority is denied with a recorded attempt and produces zero partial effect in store, index, cache or outbox.
- Local persistence, queuing, remote receipt, admission, materialization and inclusion in a receiving turn are reported independently per destination, and nothing is reported delivered to a partitioned replica.
- Erasure claims are enumerated per location and bounded to controlled stores; uncontrolled clones and retained backups are reported as unknown or not erased, never as erased or compliant.
- A purge obligation against a replica that never reconnects remains an open, aged, visible obligation rather than being silently closed.
- Byte-level fidelity — BOM, line endings, trailing whitespace, encoding, source anchor and source revision — survives replication, backup, restore and reconciliation for every record the case does not deliberately alter.
- Every negative assertion is paired with a positive control that must pass in the same run, so a blanket denial cannot be mistaken for correct enforcement.

## Instrument-can-fail controls

- IC1 scope filter OFF on the historical/tombstone path: assertion B4 (and held-out H-B4) must FAIL — the unauthorized contributor must then see the purged record's tombstone and purge metadata for the secrets/vault scope. If B4 still passes with the filter off, it was passing for an unrelated reason (record simply absent) and the coverage is void.
- IC2 deduplication OFF (redelivered event id + identical digest admitted as new): assertions A5, C3, A2 and D1-on-the-replica must FAIL — the redelivered creation event resurrects the redacted version into the replica's current applicable view and flips the release gate to QUALIFIED. This is the primary resurrection instrument.
- IC3 trust / evidence-class check OFF: assertions D3 and D1 must FAIL — the offline participant note asserting a standup sign-off promotes to an authorization, restores the removed version, and changes the action-qualification outcome.
- IC4 byte preservation OFF (normalizing writer: strip BOM, CRLF to LF, add/trim trailing whitespace, re-hash on store): assertions B5, B1 and B6 must FAIL — the untouched control record's hash diverges across stores and the retracted record's historical bytes no longer match the frozen fixture hash.
- IC5 tombstone suppression applied ONLY in the serving formatter (not at admission): assertions C2 and A4 must FAIL while A1 may still pass — proving that a pass on the current-view assertion alone is insufficient coverage and that the index/materialized path must be probed directly.
- IC6 restore watermark OFF (restored backup serves immediately; stored status=applicable field trusted): assertions A3, C4 and D1-on-the-restored-store must FAIL — the backup's pre-lifecycle content is served as current with no reconciled_through watermark.
- IC7 erasure-report honesty template OFF (report emits an unqualified global-deletion claim): assertions E1 and E2 must FAIL — the uncontrolled clone and retained backup are reported as erased instead of unknown/not erased.
- IC8 purge scoped to the primary store only (cache, outbox, export queue and embedding copies left intact): assertions B3 and A4 must FAIL — purged payload remains recoverable from at least one derived path, which is why each derived path is probed separately rather than as a group.
- IC9 (held-out only) causal dependency tracking OFF: assertions H-A6 and H-A3 must FAIL — the replacement version arriving before the redaction that motivated it is admitted with no pending-prerequisite record, leaving a window in which the removed version is served as current.
- Control protocol: each switch is flipped one at a time against an otherwise unmodified run, on a disposable store, and must produce at least one named FAILING assertion. A control that changes no assertion outcome means the corresponding assertion is passing for the wrong reason and that assertion must be redesigned before the measured run; record such a finding rather than reporting the case as covered.

## Open questions (structured list, from the validation owner's return value)

- C20 says "delete/retract/redact" without defining the terms; the oracle fixes retract / redact / purge with distinct semantics and treats "delete" as ambiguous — the implementation's vocabulary mapping must be declared and frozen before the run.
- It is unspecified whether redaction must withhold payload from the historical view as well as current serving, or only from current serving; the oracle requires withheld-in-both with metadata retained, and this needs a contract ruling since R05 (preserve prior evidence) and R19 (define redaction semantics) pull in different directions.
- Retaining the pre-redaction content hash is itself a possible disclosure channel for short secrets (brute-forceable); whether original_hash must be retained, salted or destroyed on redaction is an undecided policy question that changes assertions B2/B6 and H-B2/H-B6.
- It is unspecified whether a restored backup must be quarantined until reconciled or may serve with an explicit staleness marker; the oracle accepts either but forbids silent serving — confirm which the contract mandates before the run.
- "No unintended resurrection in current serving" does not say whether derived artifacts (embeddings, summaries, extracted graph nodes, rerank caches) that contain the removed content in transformed form count as serving; the oracle asserts they do.
- Whether a purge tombstone is scope-restricted data (the oracle's position) or a globally visible identity record is not settled by the case text and materially changes assertion B4/H-B4.
- The case does not say whether a purge obligation against a replica that never reconnects has a deadline, an escalation, or an indefinitely open state; the oracle only requires visibility, not an SLA.
- Whether a legitimately authorized new revision authored offline after the redaction (and carrying no redacted bytes) should be admitted on reconnect is not addressed by C20; the oracle admits it and asserts it must not carry the withheld payload.
- The unarchive positive control arguably belongs to C16 rather than C20; using it here as a control may double-count coverage and needs an explicit decision in the coverage map.
- Repetition counts and denominators are fixed by the trial design only for C01–C09; the oracle self-imposes 3 ordering variants x 2 repetitions for C20 and this needs agreement before the measured run.
- The case does not state whether receipts and cursors must survive a crash between the purge write and the outbox write; that boundary is C18's, but C20's tombstone durability depends on it — the ownership boundary should be named.
- Whether the erasure report is an authority record or operational telemetry (R20 says telemetry is not an immutable authority record) determines whether its per-location claims must themselves be durably evidenced.
