# C24 Oracle — "Reuse an event ID with different bytes; rename/relocate a repo; rotate a sender credential"

**Status:** independent expected outcome, written before observing any implementation output. Derived only from `acceptance-cases.md` (C24 row, go/no-go section), `requirements.md` (R01, R07, R18 are the mapped requirements; R02/R03/R04/R08/R13/R17/R19 are touched by the assertions below) and `05-verification-and-operations.md` (test-design section). No Twining source, ADR, plan or existing oracle was consulted.

**Case text being operationalised:** *Setup/trigger:* reuse an event ID with different bytes; rename/relocate a repo; rotate a sender credential. *Required observable outcome:* conflicting duplicates rejected, legitimate identity aliases preserved, new credentials scoped correctly, revoked credentials denied; no conflation of forks or users.

## 1. Abstract memory store (implementation-neutral vocabulary)

The oracle asserts over six observable surfaces. An implementation satisfies C24 if it exposes each surface by any mechanism; the names below are role names, not API names.

| Surface | Meaning | Query form used in assertions |
| --- | --- | --- |
| `EVENTS` | producer-submitted events with an identity and payload digest, whether or not admitted | `events(event_id=…)` |
| `RECORDS` | admitted, durable, addressable records | `records(record_id=…)`, `records(scope=…)` |
| `VIEW_CURRENT` | the applicable/qualifying view at a given as-of time for a given repository identity + scope | `view(repo=…, scope=…, as_of=…)` |
| `RECEIPTS` | per-event delivery state: `local_durable`, `queued`, `remote_received`, `admitted`, `rejected`, `unknown`, plus attempt count and distinct semantic effect count | `receipt(event_id=…)` |
| `VIEW_HISTORY` | the full retained lifecycle: superseded records, quarantined bytes, alias history, credential validity intervals, denial facts | `history(entity=…)` |
| `QUALIFY` | the action-gate decision surface: given (principal, credential, repository identity, scope, action), returns allow/deny with independent reasons | `qualify(principal=…, credential=…, repo=…, scope=…, action=…)` |

Digests are written as symbolic labels (`d1`, `d2`, …). The normative content is the **exact byte sequence** in the fixtures; a digest label is "the digest of those bytes under the declared algorithm". Two different byte sequences MUST NOT produce the same label.

## 4. Required observable outcome — concrete assertions

### A. Event identity, retries and conflicting duplicates (R07)

- **A-1 (positive control, durability):** `records()` contains exactly one record for `evt-7001`, `rec-7001`, whose stored bytes are byte-for-byte `P1` and whose digest is `d1`.
- **A-2 (dedup / no duplicate semantic effect):** after T03, `receipt(evt-7001).attempt_count == 2` and `receipt(evt-7001).distinct_semantic_effects == 1`; `count(records where source_event == evt-7001 and state == admitted) == 1`.
- **A-3 (receipt reconciliation):** `receipt(evt-7001).delivery_state` transitions `unknown` → `admitted` as a result of T03, and never sits at `admitted` twice with two distinct materialisations. The lost-acknowledgement window is visible in `VIEW_HISTORY` as an explicit uncertainty interval, not erased.
- **A-4 (conflicting duplicate rejected):** T04 yields `receipt(evt-7001@d2).delivery_state == rejected` with reason `event_id_reused_with_conflicting_payload`, naming both `d1` (incumbent) and `d2` (submitted). It is an explicit conflict, not a silent no-op and not an overwrite.
- **A-5 (incumbent unchanged):** after T04, `rec-7001.bytes == P1` and `rec-7001.digest == d1`; no field of `rec-7001` changed.
- **A-6 (byte preservation over normalisation):** T06 is also rejected with `event_id_reused_with_conflicting_payload` naming `d3` vs `d4`. A BOM/CRLF difference is a byte difference. `rec-7002.bytes == P3` unchanged, and `d3 != d4`.
- **A-7 (rejected bytes retained, not applicable):** the `P2` and `P3'` byte streams are retained in `VIEW_HISTORY` as quarantined conflict evidence with their own digests, author, observer, host and submit time — and are marked `applicable: false`, `evidence_class: rejected_submission`.

### B. Repository identity, aliases, forks (R01)

- **B-1 (stable identity across rename/relocate):** after T07, `resolve(remote='git@example.invalid:orchid/caldera-core.git')` and `resolve(path='/srv/work2/caldera-core')` both return repository identity `repo-9f3a-caldera` — the same identity as before T07. No new repository identity is created by T07.
- **B-2 (legitimate alias preserved):** `history(repo-9f3a-caldera).aliases` contains **both** label sets with disjoint effective intervals: `{remote: …/caldera.git, path: /srv/work/caldera, effective_until: 2026-03-02T10:00:00Z}` and `{remote: …/caldera-core.git, path: /srv/work2/caldera-core, effective_from: 2026-03-02T10:00:00Z}`. `resolve(remote='git@example.invalid:orchid/caldera.git')` still returns `repo-9f3a-caldera`, flagged `alias_status: historical`.
- **B-3 (pre-rename records survive):** `view(repo=repo-9f3a-caldera, scope='src/ingest/', as_of=2026-03-02T13:30:00Z)` == exactly `{rec-7001, rec-7002, rec-7003, rec-7004}` — a set equality, with no extra members and none of the pre-rename records dropped.
- **B-4 (no conflation of forks — identity):** `repo-2c71-caldera-fork != repo-9f3a-caldera`, despite a shared display name `caldera`, a shared local leaf path `/srv/work/caldera`, and a shared ancestor revision `rev-a1c0de`.
- **B-5 (no conflation of forks — retrieval, NEGATIVE):** `rec-7200` does **not** appear in `view(repo=repo-9f3a-caldera, …)` under any retrieval path: exact-ID lookup, scope listing, lexical search for `parser tweak`, graph-neighbour expansion from `rev-a1c0de`, semantic/dense retrieval, any cache, and any operator diagnostic endpoint. Symmetrically, `rec-7001…rec-7004` do not appear in `view(repo=repo-2c71-caldera-fork, …)`.
- **B-6 (provenance recorded independently of store location):** `rec-7200.source_repository == repo-2c71-caldera-fork` while `rec-7200.store` is whichever store holds it; the two fields are separately readable and a store move would not change `source_repository`.
- **B-7 (no unsolicited source mutation):** across T01–T15 no commit, checkout, reset or push occurs in either working tree; both trees' HEADs remain `rev-b2f1aa` and `rev-c3d9e7`.

### C. Credential rotation, scope and revocation (R18, R03, R17)

- **C-1 (rotation preserves, does not widen):** `grants(cred-k2)` == `grants(cred-k1)` exactly: `{write @ repo-9f3a-caldera : src/ingest/}`. Set equality — not a superset.
- **C-2 (positive control, legitimate write):** T11 is **admitted**; `rec-7004` exists, is attributed to principal `svc-relay-alpha`, carries `credential_at_admission == cred-k2`, and is a member of `VIEW_CURRENT` (see B-3).
- **C-3 (no retroactive invalidation):** `rec-7001`, `rec-7002`, `rec-7003` remain admitted and applicable after T10, each annotated `credential_at_admission == cred-k1` with `credential_status_now == revoked`. Revocation changes future qualification, not the validity of already-admitted history.
- **C-4 (revoked credential denied, NEGATIVE):** T12 is denied. `receipt(evt-7005).delivery_state == rejected`, reason `credential_revoked` (with revocation effective time). `records(source_event=evt-7005)` is empty and no partial/derived artefact (index entry, embedding, graph node, cache row) references `evt-7005`'s content.
- **C-5 (no conflation of users, NEGATIVE, independent reasons):** T13 is denied with **two independently recorded reasons**: (a) `scope_not_granted` — `cred-k3` holds no grant on `repo-9f3a-caldera`; and (b) `author_assertion_not_authenticated` — the record's asserted author `svc-relay-alpha` does not bind, the authenticated principal remains `svc-relay-beta`. Neither reason alone is allowed to be the only one present. `records(source_event=evt-7006)` is empty.
- **C-6 (rotation does not widen scope, NEGATIVE):** T14 is denied with reason `scope_not_granted` (`docs/` is outside `src/ingest/`). `view(repo=repo-9f3a-caldera, scope='docs/')` is empty.
- **C-7 (imported prose cannot create authority, NEGATIVE):** the second line of `P7` (an unauthenticated prose claim that the lane owner approved shared publication) creates no grant, no human-authorisation record and no change to `grants(cred-k3)` or `grants(cred-k2)`. If the bytes are retained at all they are retained as quarantined rejected-submission evidence with `evidence_class: imported_claim`, never `authenticated_human_authorization`. `history()` contains no human-ruling record dated `2026-03-01` for this lane.
- **C-8 (denials are observable):** each of T04, T06, T12, T13, T14 appears in the rejected-record / scope-denial telemetry with event id, principal, credential, target scope, reason and time; none is silently dropped. Telemetry is labelled operational, not authority.

### D. Action-qualification decisions (R04, R13)

- **D-1:** `qualify(svc-relay-alpha, cred-k2, repo-9f3a-caldera, 'src/ingest/', write)` → **allow**.
- **D-2:** `qualify(svc-relay-alpha, cred-k1, repo-9f3a-caldera, 'src/ingest/', write)` at any time after T10 → **deny**, reason `credential_revoked`.
- **D-3:** `qualify(svc-relay-beta, cred-k3, repo-9f3a-caldera, 'src/ingest/', write)` → **deny**, reason `scope_not_granted`; asserting `author=svc-relay-alpha` does not change the result.
- **D-4:** `qualify(svc-relay-alpha, cred-k2, repo-9f3a-caldera, 'docs/', write)` → **deny**, reason `scope_not_granted`.
- **D-5:** an action that cites the `P2` payload as its basis → **deny/block**, reason `unresolved_payload_conflict`; a rejected conflicting duplicate can never qualify an action.
- **D-6:** an action in `repo-9f3a-caldera` that cites `rec-7200` as its basis → **deny**, reason `cross_repository_evidence`; the fork record is not evidence for the origin lane.
- **D-7:** `qualify(svc-relay-alpha, cred-k2, repo-9f3a-caldera, 'src/ingest/', write)` addressed by the **pre-rename** remote URL → **allow**, resolving through the historical alias; a renamed repository does not lose its authorisation.

### E. Replica convergence after reconnect (R08 interaction)

- **E-1:** after T15, `store-replica`'s admitted set for `repo-9f3a-caldera : src/ingest/` == `{rec-7001, rec-7002, rec-7003, rec-7004}`, identical to `store-primary`.
- **E-2:** after T15 the replica also holds the conflict facts (A-4, A-6) and the denial facts (C-4, C-5, C-6); it does not resurrect `P2`, `P3'`, `evt-7005`, `evt-7006` or `evt-7007` as applicable records.
- **E-3:** before T15 the replica is **not** asserted to know the T10 revocation; any statement it makes about `cred-k1` while offline must be marked stale/unknown rather than confidently current.

N-3 no admitted record is ever attributed to `svc-relay-alpha` on the strength of `cred-k3`. N-4 no record exists for `evt-7005`, `evt-7006` or `evt-7007`. ## 6. Positive controls (summary)

PC-1 (C-2) legitimate write under the rotated credential is admitted and applicable. PC-2 (B-2/D-7) the pre-rename remote URL still resolves and still qualifies — proving the identity check is not simply denying everything. PC-3 (A-2/A-3) the byte-identical retry reconciles to a single acknowledged effect — proving dedup is real rather than blanket rejection of repeats. PC-4 (B-6) the fork's own write is admitted **in the fork's scope** — proving isolation is not blanket suppression.

## 7. Pass/fail

C24 passes only if every A/B/C/D/E assertion holds **and** every instrument control in `instrument_controls` produces the named failure when its switch is flipped. Any of the following is an immediate rejection under the go/no-go criteria regardless of the rest: an admitted record for `evt-7005`/`evt-7006`/`evt-7007` (unauthorised action / authority-changing error), `rec-7200` surfacing in origin scope (cross-scope disclosure), a human-ruling record created from `P7` prose (fabricated human ruling), or `rec-7001` silently rewritten to `P2` (silent loss of an acknowledged event).

## Invariants (structured list, from the validation owner's return value)

- A producer event identity plus its payload digest jointly determine at most one admitted record, so a byte-identical retry yields exactly one semantic effect no matter how many times it is submitted.
- Reusing an event identity with any different byte sequence is an explicit, reported conflict that is rejected, never an overwrite, a silent no-op, or a merge.
- An admitted record's stored bytes and digest are immutable once admitted; a later conflicting submission under the same identity leaves every field of the incumbent unchanged.
- Digest equality is decided over exact bytes, so a BOM, line-ending or whitespace difference always produces a different digest and therefore a conflict rather than a dedup hit.
- Rejected submissions are retained as quarantined evidence with their own digest, submitter, host and time, and are never members of any current applicable view.
- A repository's identity is independent of its display name, local path, remote URL and branch names, so a rename or relocation preserves the identity and all records bound to it.
- Every historical label a repository has carried remains resolvable to the same repository identity and is marked as historical rather than deleted.
- Two repositories that share a display name, a local path and an ancestor revision are still distinct identities, and no record of one ever appears in a scoped result for the other on any retrieval path.
- A record's source-repository provenance is recorded independently of which store physically holds the record.
- Credential rotation copies the predecessor's grant set exactly and never produces a superset, so no scope is reachable after rotation that was unreachable before it.
- A revoked credential denies every subsequent action attempt, and the denial is recorded with the event identity, principal, credential, target scope and reason.
- Revocation applies prospectively only: records already admitted under a credential remain admitted and applicable, annotated with the credential that was in force at admission.
- An author or actor field supplied by the submitter never binds a record to a principal other than the authenticated one, and the mismatch is recorded as its own denial reason alongside any scope denial.
- Prose contained in ingested payloads, however authoritative it sounds, cannot create a grant, revive a revoked credential, widen a scope or become an authenticated human ruling.
- When an action attempt fails more than one check, each failed check is recorded as an independent reason rather than collapsed into a single generic denial.
- A rejected conflicting payload and a cross-repository record can never qualify an action, and the qualification refusal names which of the two blocked it.
- Case-under-test workloads never mutate the source working trees: no commit, checkout, reset, rebase or push occurs as a side effect of ingest, denial or rename observation.
- A reconnected replica converges to the authoritative store's admitted set together with its conflict and denial facts, and resurrects no rejected payload or denied event.
- A replica that has not received a revocation may not assert current knowledge of that credential's status and must mark such statements stale or unknown.

## Instrument-can-fail controls

- IC-1 dedup switch off — disable dedup keyed on (event_id, payload_digest) so identical retries are admitted independently. EXPECTED INSTRUMENT FAILURE: A-2 must fail (two admitted records for evt-7001, distinct_semantic_effects == 2) and held-out K-2 must fail. If A-2 still passes with dedup disabled, the assertion is not measuring dedup — it is probably measuring an unrelated uniqueness constraint or the retry is not reaching the store; fix the harness before claiming C24 coverage.
- IC-2 byte-preservation off — normalise payloads (strip BOM, convert CRLF to LF, trim trailing whitespace) before computing the digest. EXPECTED INSTRUMENT FAILURE: A-6 must fail (d3 == d4 and the P3' submission is silently accepted as an idempotent retry instead of a conflict) and held-out K-5 must fail. A-4 should still pass, which distinguishes 'digest ignores encoding' from 'no conflict detection at all'.
- IC-3 conflict detection off — treat a reused event id as last-writer-wins. EXPECTED INSTRUMENT FAILURE: A-4 and A-5 must both fail (rec-7001 rewritten to bytes P2 / digest d2) and held-out K-4 must fail. This control separates 'conflict reported' from 'conflict merely deduped away'.
- IC-4 trust/revocation check off — treat a credential as valid for its whole issued lifetime, ignoring the revocation timestamp. EXPECTED INSTRUMENT FAILURE: C-4 must fail (evt-7005 admitted, a record appears under cred-k1 after T10) and D-2 must flip to allow; held-out M-4 and N-2 must fail. Note that this is an immediate-rejection-class outcome in a real run, so it is only ever exercised in the instrument-control arm against a disposable store.
- IC-5 author-assertion binding on — let the submitted author field set the record's principal. EXPECTED INSTRUMENT FAILURE: C-5 must fail on its second reason (record attributed to svc-relay-alpha while the authenticated principal was svc-relay-beta) and held-out M-5 must fail. The scope-denial half of C-5 should still fire, proving the two reasons are recorded independently rather than as one collapsed check.
- IC-6 scope filter off before ranking — remove the repository/scope predicate from retrieval so ranking runs over the whole corpus. EXPECTED INSTRUMENT FAILURE: B-5 must fail (rec-7200 surfaces in a repo-9f3a-caldera lexical or dense query for 'parser tweak') and held-out L-5 must fail. Run this control against every path separately — exact-ID, lexical, dense, graph expansion, cache and diagnostics — because a filter can be present on one path and absent on another.
- IC-7 alias resolution off — key repository identity on the current remote URL or current path instead of a stable identity. EXPECTED INSTRUMENT FAILURE: B-3 must fail (rec-7001, rec-7002 drop out of the post-rename view, or a second repository identity appears), B-2 must fail, and D-7 must flip to deny; held-out L-1, L-2, L-3 and N-7 must fail. If B-3 still passes, the assertion is being satisfied by something other than identity stability.
- IC-8 path-based identity collapse on — merge repositories that share a local leaf path or display name. EXPECTED INSTRUMENT FAILURE: B-4 and B-5 must fail (repo-2c71-caldera-fork merges into repo-9f3a-caldera; rec-7200 joins the origin view) and held-out L-4 and L-5 must fail. This is the conflation control and is distinct from IC-6: IC-6 leaks across a correct boundary, IC-8 erases the boundary.
- IC-9 rotation grant-copy widened — on rotation, grant the successor credential the union of every scope the principal has ever held, or repository-wide write. EXPECTED INSTRUMENT FAILURE: C-1 and C-6 must fail (evt-7007 admitted at docs/, grants(cred-k2) a proper superset of grants(cred-k1)) and held-out M-1, M-6 and N-4 must fail.
- IC-10 instruction/data boundary off — let ingested payload prose be parsed as policy. EXPECTED INSTRUMENT FAILURE: C-7 must fail (a grant or human-authorisation record is created from line 2 of P7) and held-out M-7 must fail, including the key-t7 revival clause. Because this is a fabricated-human-ruling class outcome, run it only in the disposable instrument-control arm.
- IC-11 rejected-bytes retention off — discard conflicting and denied payloads instead of quarantining them. EXPECTED INSTRUMENT FAILURE: A-7 must fail (P2 and P3' not present in VIEW_HISTORY) and held-out K-6 must fail, while A-4 and A-5 still pass — which proves A-7 is measuring retention and not merely rejection.
- IC-12 denial telemetry off — suppress rejected-record and scope-denial reporting. EXPECTED INSTRUMENT FAILURE: C-8 must fail and held-out M-8 must fail, while the admission assertions all still pass — proving the observability assertion is independent of the enforcement assertions and that a silent denial would have been caught.
- IC-13 replica sync ignores negative facts — propagate admitted records but not conflicts or denials. EXPECTED INSTRUMENT FAILURE: E-2 must fail and held-out P-2 must fail, while E-1/P-1 still pass — proving convergence is being checked over histories and receipts, not only over admitted row counts.
- IC-14 offline freshness marking off — let the offline replica answer credential-status queries as if current. EXPECTED INSTRUMENT FAILURE: E-3 must fail and held-out P-3 must fail (the replica asserts cred-k1 valid or invalid as current fact during its offline window instead of marking it stale/unknown).
- IC-15 positive-control sanity (inverse control) — disable nothing, but assert that the four positive controls pass. If PC-1 through PC-4 ever fail while every negative assertion passes, the system is passing C24 by refusing everything; a blanket-deny implementation must be reported as a failure, not as coverage.

## Open questions (structured list, from the validation owner's return value)

- C24 says conflicting duplicates are 'rejected' but not whether the conflicting bytes must be retained; the oracle requires retention as quarantined non-applicable evidence (reading R02 'unknown data remains unknown' and R07 'explicit conflict' together), and this should be confirmed before the measured run because a system that discards the bytes would fail A-7/K-6 on an interpretation choice rather than a defect.
- The case does not state whether a conflicting reuse should be rejected or instead admitted under a derived distinct identity (e.g. id+digest); the oracle chooses rejection-plus-quarantine, and the alternative would change A-4/K-4 from a rejection assertion to a distinct-identity assertion.
- Whether revocation is prospective-only or retroactive is unspecified; the oracle asserts prospective-only (C-3/M-3), which is the lower-risk reading of R05 'preserve prior evidence' but directly contradicts a threat model where the rotated key is believed compromised.
- If a credential is rotated because the predecessor was compromised, the correct disposition of records admitted under it before revocation is undefined; the oracle marks them applicable-with-credential-status rather than quarantining them, and a compromise-aware policy would need a separate case.
- The case does not say whether a rename observed by a single host adapter is sufficient to re-bind identity, or whether independent confirmation is required; the oracle treats it as connector-observed evidence sufficient to update aliases but not to create authority, per R03's evidence-class separation.
- Whether resolution by a historical repository label must succeed, warn, or fail is unspecified; the oracle requires it to succeed with an explicit historical marker (B-2/L-2), which is a design choice that a stricter implementation might reasonably refuse.
- The basis for distinguishing a fork from the origin is unstated — declared identity, remote URL, shared history, or an explicit registration; the oracle asserts only that they must not be conflated, and deliberately does not prescribe the discriminator, but a system with no repository-registration step may have no non-heuristic way to pass B-4/L-4.
- The interaction between C24 revocation and C19 offline behaviour is not spelled out for the specific case where a queued-but-unacknowledged event was signed before revocation and admitted after it; the oracle does not assert an outcome for that ordering and it should be pinned before the run.
- Whether an event denied on scope or credential grounds may still consume an event identity (blocking a later legitimate use of the same id) is unspecified; the oracle is silent and a follow-up case should fix it.
- The required granularity of denial reasons is not specified; the oracle requires both reasons for the cross-principal attempt (C-5/M-5), which is stricter than the case text and should be agreed rather than assumed.
- 'No conflation of users' is asserted here only for the service-principal layer; whether the human operator behind a service principal must also be separately resolvable in every record is left to R01's 'where applicable' and is not asserted in this oracle.
- The case does not declare a hash algorithm or an encoding-declaration requirement, so the oracle uses symbolic digest labels; the declared algorithm and its encoding metadata must be fixed in the run manifest for A-6/K-5 to be checkable as a concrete value rather than an inequality.
