# C17 Oracle — "Truncated/conflicted export, missing file, shallow/sparse checkout, incompatible schema or partially downloaded batch"

**Validation owner artifact. Authored before any observation of the implementation.** Expected outcomes below are derived only from `acceptance-cases.md` (C17 row, plus the coverage map R02/R07/R09/R19), `requirements.md` and `05-verification-and-operations.md`. No Twining source, ADR, plan or existing oracle was consulted.

Case text under test: *"Quarantine/refuse or defer according to contract; retain prior valid evidence. Incomplete absence is not deletion; no unreported fallback to an old valid-looking projection."*

---

## 1. Abstract memory-store model

The assertions are written against an abstract store, not an API. Any implementation must expose an equivalent of each surface; if it cannot, that is a *fail*, not a *not-applicable*.

| Surface | Meaning |
| --- | --- |
| `events(event_id)` | Producer-emitted durable units with stable identity, payload digest, exact bytes, scope, revision, evidence class. |
| `records(record_id, version)` | Admitted, materialized items with lifecycle state: `current`, `superseded`, `revoked`, `quarantined`, `deferred`, `unknown`. |
| `current_applicable_view(scope)` | What the store would serve *now* for a scope, with per-item `freshness` and `observation_coverage`. |
| `historical_view(record_id)` | Every prior version and disposition, with original bytes and hashes retained. |
| `receipts(event_id)` | Seven independently observable states: `local_durable`, `queued`, `remote_received`, `admitted`, `materialized`, `indexed`, `injected` (plus optional `task_acked`). Collapsing these into one boolean fails A24. |
| `ingest_attempts(artifact_id)` | One entry per import attempt: disposition (`ADMIT` / `QUARANTINE` / `REFUSE` / `DEFER` / `REPORT_NOT_OBSERVED`), reason code, observed vs declared byte lengths, retained original bytes + hash, retry count. |
| `action_qualification(action, scope)` | `QUALIFIED` / `REFUSED` / `DEFERRED` with reason codes, `missing[]`, `fallback_used`, `fallback_source`. |
| `coverage_report()` | Per-scope observation status of the current checkout/replica. |

**Declared-contract parameter.** C17 says "according to contract" but does not fix the contract, so the validation owner fixes it *before* the run. For the development variant: admission granularity is **ARTIFACT_ATOMIC**, and the disposition map is truncated→QUARANTINE, missing part→DEFER, unsupported schema→REFUSE, duplicate-ID-conflicting-bytes→QUARANTINE, sparse/shallow non-observation→REPORT_NOT_OBSERVED. If the implementation declares a different but self-consistent contract *before observation*, the assertions are re-bound to it and the substitution is recorded as an oracle change with a source/requirement reason (per `acceptance-cases.md` line 3). A contract declared *after* seeing a failure is not admissible.

## 5. Required observable outcome

### 5.1 Retain prior valid evidence
- **A1 (positive).** After every failed import (S1, S2, S4, S5) every seeded record retains its exact byte hash, encoding, newline style and BOM flag from S0. `rec-ORCH-2`'s CRLF+BOM survives unchanged.
- **A16 (positive).** Every quarantined or refused artifact's stored bytes hash equals its observed hash at ingest, with `normalized = false`.
- **A17 (positive).** After S9 the S1/S4/S5 quarantine entries remain inspectable in the historical view with original bytes and reason codes — repair does not erase the record of the failure.
- **A19 (positive control).** `rec-ORCH-1` is retrievable and byte-identical at every step S0→S8.

### 5.2 Quarantine / refuse / defer per contract
- **A2 (negative).** `rec-ORCH-6`, carried only by the truncated part, never appears in any current applicable view before S9.
- **A3 (positive).** The S1 attempt records observed 1790 vs declared 3072 and an explicit completeness state `INCOMPLETE`.
- **A4 (positive).** The S2 attempt yields `DEFER` naming missing part 4 and missing events `evt-105`, `evt-106`.
- **A8 (positive).** S4 yields `REFUSE` / `UNSUPPORTED_SCHEMA` with bytes retained at the original hash.
- **A9 (negative).** No record from the 2.0 artifact is admitted with unknown fields dropped, and the stored artifact is not rewritten into 1.4 shape (R19 old-client-corruption rule, inverted: the *new* client must not corrupt the *newer* semantics either).
- **A10 / A11.** The S5 entry retains **both** conflicting bodies for `evt-103` under two distinct hashes (positive); neither becomes current and `rec-ORCH-2` stays at v1 until S9 (negative).
- **A15 (positive).** S8 produces the same quarantine entry identity, `retry_count` incremented, no new events, records or view changes.

### 5.3 Incomplete absence is not deletion
- **A5 (negative).** No absence produced at S2 or S3 is represented as deletion, retraction or tombstone. Queries for `evt-105`, `evt-106` and `rec-ORCH-3` return `UNKNOWN` or `NOT_OBSERVED`, never `DELETED`.
- **A6 (positive).** A coverage report after S3 states `docs/ops/ : NOT_OBSERVED (cause = SPARSE_FILTER)`, and `rec-ORCH-3` remains served from its previously admitted local copy.
- **A7 (positive).** Revisions behind the depth-1 boundary are labeled `HISTORY_UNAVAILABLE`, not absent or nonexistent.
- **A23 (negative).** No tombstone or deletion event is emitted at any step.

### 5.4 No unreported fallback to an old valid-looking projection — the centerpiece
Between S2 and S9, `rec-ORCH-4@v1` is locally present, syntactically valid, and **wrong**: a revocation exists upstream in the part that failed to land, and the manifest proves the store *knows* a newer version is pending.

- **A12 (positive).** Any answer or context packet serving `rec-ORCH-4@v1` in that window carries `fallback_used = true`, the fallback source identity (`local projection dated 2026-09-08T14:10:00Z`) and reason `PENDING_UNRESOLVED_IMPORT:batch-2026-09-15T10-00Z`.
- **A13 (negative).** The action-qualification decision for `publish-ledger-release` at S6 is **never `QUALIFIED`**. Required reasons include `PENDING_UNRESOLVED_IMPORT` and `MISSING_EVENTS:evt-105,evt-106`.
- **A20 (positive).** After S9 the action is `REFUSED` with reason `AUTHORIZATION_REVOKED:rec-ORCH-4@v2` — demonstrating that a QUALIFIED verdict at S6 would have been an authority-changing error under the go/no-go criteria, not a latency nicety.

### 5.5 Isolation and evidence class (carried constraints)
- **A14 (negative).** The prose claim embedded in `evt-104` does not change any evidence class, does not create a human authorization, and does not cause admission of the deferred parts. Its caller-controlled `promoted_by`, `active` and `MUST` fields confer nothing (R03/R17).
- **A21 (negative).** `rec-DECOY-9` never appears in any view, ranked candidate list, quarantine reference, diagnostic endpoint or qualification reason — including operator diagnostics (R13/R16).
- **A24 (positive).** The seven receipt states are individually observable and not collapsed into one boolean.
- **A22 (positive).** The `store-CIR` rebuild reproduces the same current view, historical view and the same three quarantine entries with identical hashes.

### 5.6 End state after S9 (abbreviated; full form in fixtures)
`src/ledger/`: `rec-ORCH-1@v3`, `rec-ORCH-4@v2` (revocation), `rec-ORCH-5@v1`, `rec-ORCH-6@v1`. `src/ledger/posting/`: `rec-ORCH-2@v2`. `docs/ops/`: `rec-ORCH-3@v1` flagged `NOT_OBSERVED_BY_CURRENT_CHECKOUT` / `UNKNOWN_NOT_DELETED`, plus `rec-ORCH-7@v1`. Historical view retains `rec-ORCH-4@v1` as `revoked` with original bytes. Quarantine ledger holds three entries. `tombstone_events_emitted = []`, `deletion_events_emitted = []`, and `rec-DECOY-9` is absent from every surface.

## 7. Instrument-can-fail controls

See `instrument_controls`. Each control is run as a separate arm with one switch disabled; the named assertion **must flip from pass to fail**. If a control arm still passes, the assertion is passing for the wrong reason and does not count as coverage (`05-verification-and-operations.md`, "Prove instruments can fail").

## 8. Oracle change policy

Original and corrected outcomes are both retained. Any change to an expected disposition requires a written source/requirement reason naming the clause. Thresholds and dispositions may not be relaxed after seeing a failure without reporting the original result and an explicit scope decision.


## Invariants (structured list, from the validation owner's return value)

- A failed, quarantined, refused or deferred ingest never changes the bytes, hash, encoding, newline style, BOM flag or lifecycle state of any record already admitted before it.
- An artifact whose observed byte length disagrees with its manifest's declared length is never treated as complete, regardless of whether any of its entries were admissible.
- A record carried only by a truncated, refused, conflicted or missing portion of a transfer never enters any current applicable view.
- Failure to observe a record - because a part is missing, a segment is partially downloaded, a checkout is shallow or a replica is sparsely filtered - is represented as UNKNOWN or NOT_OBSERVED and never as deletion, retraction or tombstone.
- No tombstone or deletion event is emitted anywhere in the C17 sequence, because nothing in C17 is actually deleted.
- History that is unreachable because of clone depth is labeled HISTORY_UNAVAILABLE and never reported as nonexistent.
- Every quarantined or refused artifact retains its original bytes at its original ingest hash, with no normalization of line endings, byte-order marks or encodings.
- Two bodies sharing one event or entry identity with different digests are retained as an explicit conflict with both hashes preserved, and neither becomes the current version.
- An artifact declaring an unsupported schema is refused whole, is never coerced by dropping unknown required fields, and is never rewritten into a supported schema's shape in storage.
- Re-ingesting a byte-identical failed artifact is idempotent: same quarantine identity, incremented retry count, no new events, records or view changes.
- Whenever the store serves a locally held version while knowing a newer version is pending in an unresolved transfer, the answer carries an explicit fallback marker naming the fallback source and the pending transfer.
- A consequential action is never qualified from evidence the store knows to be possibly superseded by an unresolved transfer; the decision is refusal or deferral with the missing identities named.
- Prose carried inside imported data - and caller-controlled fields such as promoted_by, active or a MUST heading - never changes an evidence class, creates a human authorization, finalizes a deferred transfer or qualifies an action.
- Out-of-tenant or out-of-repository records sharing a mutable label or near-identical prose never appear in any view, candidate list, quarantine reference, diagnostic output or qualification reason.
- The seven exchange states (local durable, queued, remotely received, admitted, materialized, indexed, injected) are independently observable per event and are never collapsed into a single admitted flag.
- A clean, complete, in-schema, non-conflicting transfer is admitted normally at every step, so refusal behavior is never satisfied by refusing everything.
- Repairing a failed transfer admits the missing content without erasing the historical record of the failure, its reason code or its retained original bytes.
- A rebuild from durable export on a machine with no prior state reproduces the same current view, the same historical view and the same quarantine ledger with identical hashes.

If A21 still passes with the filter off, the decoy was never reachable and A21 was not testing scope enforcement.
- IC-2 trust_check_off - disable evidence-class and instruction-isolation enforcement so caller-supplied promoted_by/active/MUST fields are honored; A14 and A13 (held-out B14 and B13) must flip to FAIL because the embedded prose promotes to human authorization and qualifies publish-ledger-release / cut-dispatch-tag.
- IC-3 dedup_off - disable artifact-digest and event-identity deduplication; A15 (held-out B15) must flip to FAIL because the byte-identical re-ingest at S8/H8 creates a second quarantine entry with a new identity or re-applies semantic effects.
- IC-4 byte_preservation_off - enable normalization on ingest (strip BOM, canonicalize CRLF to LF, re-encode utf-16le to utf-8); A16 must flip to FAIL because a stored hash no longer matches its ingest hash, and A10 (held-out B10) must also flip because the two conflicting bodies of evt-103 / ntr-203 normalize to a single hash and the conflict disappears.
- IC-5 completeness_check_off - ignore manifest part/segment counts and declared byte lengths; A2, A3 and A4 (held-out B2, B3 and B4) must flip to FAIL because the truncated record is admitted, the INCOMPLETE state is never recorded, and the missing-part deferral never fires.
- IC-6 freshness_annotation_off - strip pending-transfer staleness annotations from served records; A12 and A13 (held-out B12 and B13) must flip to FAIL because the old valid-looking projection is served unmarked and the consequential action qualifies from it - this is the control that proves the centerpiece assertion is live.
- IC-7 schema_negotiation_off - accept unknown schema versions by dropping unrecognized required fields; A9 (held-out B9) must flip to FAIL because records from the 2.0 / 4.0 artifact are admitted in coerced form.
- IC-8 absence_semantics_off - treat non-observation as authoritative absence; A5 and A23 (held-out B5 and B23) must flip to FAIL because the sparse/shallow checkout and the missing part emit deletions or tombstones for rec-ORCH-3, evt-105 and evt-106 / blk-4023, ntr-206 and ntr-207.
- IC-9 scoped_relation_check_off (held-out set) - disable scope boundaries on supersession, so a narrowing successor is applied as a general replacement; B20 must flip to FAIL because blk-4044@v2 re-qualifies the whole-service tag cut instead of refusing it outside services/dispatch/routing/.
- Control-arm meta-rule: each control is run as an isolated arm with exactly one switch disabled and everything else fixed; an arm in which the named assertion still PASSES means that assertion was passing for the wrong reason and does not count as C17 coverage, and the arm itself must be reported rather than silently re-run.

## Open questions (structured list, from the validation owner's return value)

- C17 says 'according to contract' but names no contract, so which failure mode maps to quarantine, refusal or deferral is undefined; this oracle fixes the mapping in advance and re-binds to any contract the implementation declares before observation, but the programme should state whether a per-failure-mode contract is permitted at all or whether one disposition is mandatory for a whole class.
- Admission granularity for a truncated or partially downloaded transfer is unspecified: may complete records preceding the truncation point be admitted (record-atomic), or must the whole artifact be rejected (artifact-atomic)? The oracle runs one branch in the development set and the other in the held-out set rather than assuming.
- 'No unreported fallback to an old valid-looking projection' forbids the unreported case but does not say whether a *reported* fallback may still qualify a consequential action; this oracle reads R04/R12 as forbidding qualification in that state, but the case text alone does not settle it.
- The case does not say whether non-observation must be reported per scope, per record, or both; the oracle requires a per-scope coverage report plus per-record annotation, which may be stricter than intended.
- 'Incomplete absence is not deletion' leaves open when an absence may legitimately become a deletion - i.e. what constitutes a complete enough observation to admit a tombstone - and the programme should define that threshold since C20 depends on it.
- Retention policy for quarantined bad bytes is unstated: how long must an implementation keep a refused artifact, and does a retention expiry count as losing evidence under R02/R19?
- For a non-Git transport, the case does not name the equivalent of a shallow or sparse checkout; this oracle treats a depth-limited, path-filtered partial replication as the equivalent, and per line 43 the report must still separately state the disposition of the Git-specific role rather than marking it covered.
- Whether a store may continue serving a scope at all while a transfer touching that scope is unresolved - as opposed to serving with a fallback marker - is a policy choice the case does not fix; the oracle permits serving with a marker and forbids only qualification.
- The case does not say whether a conflicted transfer must be quarantined as a whole artifact or only at the conflicting identity; the development variant assumes whole-artifact and the held-out variant assumes per-identity, and the discrepancy should be resolved before the measured run.
